## 1 — Architecture

### 1.1 Class hierarchy

```
                 ComponentBase
                       │
                 InputBase<TValue>     ← Microsoft.AspNetCore.Components.Forms
                       │
       ┌───────────────┼───────────────┬───────────────┐
       │               │               │               │
  LipiTextBox    LipiTextArea   LipiNumberInput   LipiSelectBase<TValue, TItem>
                                  <TValue>             (abstract)
                                                          │
                                                ┌─────────┴─────────┐
                                                │                   │
                                          LipiSelect          LipiCombobox
                                          <TValue>            <TValue, TItem>
                                          (TItem = TValue)    (caller-typed)
```

`LipiSelectBase<TValue, TItem>` is an abstract intermediate that holds the shared select state machine (search, dropdown open/close, keyboard navigation, virtualization, JS positioning interop). The two concrete subclasses differ only in how they extract value/label from items:

- `LipiSelect<TValue> : LipiSelectBase<TValue, TValue>` — identity selectors. `ItemValue(item) = item`, `ItemLabel(item) = item.ToString()`.
- `LipiCombobox<TValue, TItem> : LipiSelectBase<TValue, TItem>` — caller-provided `ValueSelector` + `LabelSelector` lambdas + optional `ItemTemplate` / `SelectedAnchorTemplate` `RenderFragment<TItem>`.

### 1.2 Why `InputBase<TValue>` derivation (not `ComponentBase`)

Three things come for free with `InputBase<TValue>`:

1. **`@bind-Value` two-way binding** — `Value` / `ValueChanged` / `ValueExpression` parameters are inherited and parsed by the compiler when the user writes `@bind-Value="model.Foo"`.
2. **`EditContext` integration** — components automatically register with the parent `EditForm`'s validation pipeline. `ValidationMessage<For>` works without any custom wiring.
3. **`CurrentValue` / `CurrentValueAsString`** — the framework's TValue-aware setters that round-trip through `TryParseValueFromString` and `FormatValueAsString` for free.

The trade-off: every component must implement `TryParseValueFromString` (string → TValue) and may override `FormatValueAsString` (TValue → string). For `LipiTextBox` (TValue = string?), parse is identity. For `LipiNumberInput<TValue>`, parse uses `BindConverter` with the effective culture. For the select family, parse cascades label-match → value-string-match → AllowFreeText.

### 1.3 State precedence

All five components compute a single `ResolvedState` enum value from a strict cascade:

```
Disabled > ReadOnly > Error > Success > Warning > RequiredEmpty > Default
```

The first state in the chain whose condition is true wins. Multiple state parameters can be bound simultaneously without conflict — only the highest-precedence one renders. Examples:

- `Required="true" Error="..."` → renders Error (apricot tint suppressed; red border + helper take over)
- `ReadOnly="true" Warning="..."` → renders ReadOnly (warning helper not shown)
- `Disabled="true" Required="true"` → renders Disabled (no apricot tint)

This avoids state-conflict logic at every call site. The component handles precedence; the caller just describes truths.

## 4 — Required-field visual style (apricot tint)

Decision A12 (token foundation, May 4) added the apricot-tint pattern as the default required-field visual signal, with opt-out to `AsteriskOnly`.

### 4.1 Behavior

- **`Required="true"` AND `Value` empty AND state is Default**: wrapper gets `lipi-input-state-required-empty` class. The field background tints apricot (fade-in, not full saturation). The asterisk renders next to the label.
- **As soon as `Value` becomes non-empty**: state transitions to Default. Apricot tint fades to white. Asterisk remains (it indicates the rule, not the current state).
- **`Required="true"` AND `Error` set**: state precedence elevates to Error. Apricot tint suppressed; red border + helper + icon take over.

### 4.2 Opt-out

Two paths:

1. **Per-component**: pass `RequiredVisualStyle="RequiredVisualStyle.AsteriskOnly"` to disable tint for that one input.
2. **App-wide**: configure `LipiInputDefaults.RequiredVisualStyle = AsteriskOnly` in `Program.cs`. All inputs inherit unless they override.

### 4.3 Reasoning (recap from A12)

Industry norm is asterisk-only (Material UI, Ant, Carbon, Chakra, MudBlazor, Telerik, Syncfusion, Salesforce, Primer all use this). Field tinting is rare; closest precedents are GOV.UK and some Japanese form patterns.

For HIS context the trade-off shifts: reception scans 30-field patient registration under time pressure with high error cost. Apricot tint provides cognitive scaffolding ("what's still missing at a glance") while pairing with asterisk + ARIA so accessibility is solid. Fade-on-fill addresses scale calmness — the form de-emphasizes after each field is filled.

Default with opt-out path lets us reassess after PatientNew migration sees it on a real form at scale.

## 5 — Confidence pills

Decision A12 also introduced four confidence levels rendered as small pills next to the label:

| Level | Pill class suffix | Backing tokens |
|-------|-------------------|----------------|
| Verified | `verified` | `--color-confidence-verified-{bg,text}` |
| Self-reported | `self` | `--color-confidence-self-{bg,text}` |
| Estimated | `estimated` | `--color-confidence-estimated-{bg,text}` |
| Unknown | `unknown` | `--color-confidence-unknown-{bg,text}` |

Composition pattern (light mode):

- Verified ← success-pale bg + success-text-strong → green theme
- Self-reported ← info-pale bg + info-text-strong → blue theme
- Estimated ← warning-pale bg + warning-text-strong → amber theme
- Unknown ← bg-subtle + text-secondary → neutral grey

ARIA: pill wrapper has `aria-label="Data confidence: {Level}"` so screen readers announce the meaning.

Used by:

- DOB confidence (Decision #5): Verified DOB locked from edits unless SysAdmin/SiteAdmin override
- Identity verification status: Aadhaar / ABHA verified vs claimed
- Lab result reliability: instrument-measured vs self-reported

## 6 — `LipiInputDefaults` (DI configuration)

Single configuration class injected via `IOptions<LipiInputDefaults>` into every component. App-wide defaults that components consume only when their per-instance parameter is null.

```csharp
public sealed class LipiInputDefaults
{
    public RequiredVisualStyle RequiredVisualStyle { get; set; } = RequiredVisualStyle.ApricotTint;
    public bool   AlwaysReserveHelperSlot { get; set; } = true;
    public string NumberLocale            { get; set; } = "en-IN";
}
```

### 6.1 Registration

```csharp
// Program.cs
builder.Services.Configure<LipiInputDefaults>(opts =>
{
    opts.RequiredVisualStyle      = RequiredVisualStyle.ApricotTint;
    opts.AlwaysReserveHelperSlot  = true;
    opts.NumberLocale             = "en-IN";
});
```

### 6.2 Why DI options (not static fields)

Per-Anthropic-tenant overrides become trivial: each clinic database can have its own DI registration scope. Static fields would require app restart to flip a default.

### 6.3 `AlwaysReserveHelperSlot`

When `true` (default), every component reserves a 16px helper-text row even when no helper / error / warning / success is set. This prevents the "field jumps down by 16px when validation fires" UX glitch. When `false`, the helper row only renders when there's content to show — denser layouts but unstable vertical rhythm during validation.

## 7 — `AutocompleteValidator` (HTML5 token validation)

When a caller passes `Autocomplete="given-name"`, that string is validated against the HTML5 `autocomplete` token list. Invalid tokens trigger:

- **Development**: `InvalidOperationException` at `OnParametersSet` (env-gated by `IWebHostEnvironment.IsDevelopment()`)
- **Production**: `ILogger.LogError` + render with `autocomplete="off"` fallback (warn-and-fallback pattern)

### 7.1 Common typo corrections (curated)

| Caller passed | Validator suggests |
|---------------|--------------------|
| `country-name` | `country` |
| `organization-title` | `off` (no canonical token; use `off`) |
| `organization-type` | `off` |
| `phone` | `tel` |
| `mobile` | `tel` |
| `email-address` | `email` |
| `postal-code` | `postal-code` (already correct) |
| `zip` | `postal-code` |
| `dob` | `bday` |

Full token list: see `AutocompleteValidator.IsValid` source. Standard categories include name (`given-name` / `family-name` / `additional-name`), contact (`tel` / `email`), address (`street-address` / `address-line1` / `postal-code` / `country`), and credentials (`username` / `current-password` / `new-password`).

### 7.2 Why validate at all

Wrong autocomplete tokens silently break browser auto-fill. A reception staff form that uses `autocomplete="phone"` instead of `autocomplete="tel"` won't auto-populate from saved profiles — invisible UX degradation. Validator catches typos at component-instantiation time.

## 8 — Locale handling (`LipiNumberInput<TValue>`)

### 8.1 Default and override path

Default locale is `en-IN` (DI configurable). Per-instance override via `Locale="en-US"`. The component computes `EffectiveCulture` once per render:

```csharp
private CultureInfo EffectiveCulture
{
    get
    {
        var name = !string.IsNullOrWhiteSpace(Locale)
                 ? Locale
                 : Defaults.Value.NumberLocale;
        try { return CultureInfo.GetCultureInfo(name); }
        catch (CultureNotFoundException)
        {
            Log.LogWarning("[LipiNumberInput] Unknown locale '{Locale}', falling back to en-IN", name);
            return CultureInfo.GetCultureInfo("en-IN");
        }
    }
}
```

### 8.2 Display semantics

Two display modes per component:

- **`RawDisplay`** (when input has focus): `0.################` format — preserves all entered digits without grouping. User sees what they typed.
- **`FormattedDisplay`** (on blur): `N0` for integers, `N{DecimalPlaces}` for explicit, `N` (culture default) otherwise. Grouping applied per locale.

### 8.3 Locale comparison (same value: `123456.78`)

| Locale | RawDisplay | FormattedDisplay (decimal, 2 places) |
|--------|------------|--------------------------------------|
| en-IN | `123456.78` | `1,23,456.78` |
| en-US | `123456.78` | `123,456.78` |
| de-DE | `123456,78` | `123.456,78` |
| ja-JP | `123456.78` | `123,456.78` (NumberDecimalDigits=0 by default) |

The decimal separator on RawDisplay matches locale (en-IN/en-US use `.`, de-DE uses `,`). Input filtering respects the locale's decimal separator.

### 8.4 Why en-IN default

LiPi HIS is an Indian HIS. Most clinical numbers (lab values, prescription doses, billing) display naturally with Indian grouping. en-US is the override path for non-Indian deployments.

## 9 — Architectural decisions (the engineering calls)

These are decisions made during component build that aren't obvious from the API surface. Documented for future debugging and to inform sibling component decisions.

### 9.1 `dynamic` arithmetic in stepper code path

`LipiNumberInput<TValue>.AddStep(...)` uses `dynamic` dispatch to perform arithmetic on the unknown numeric type:

```csharp
var underlying = Nullable.GetUnderlyingType(typeof(TValue)) ?? typeof(TValue);
var c = current ?? (TValue)Convert.ChangeType(0, underlying)!;
var s = step    ?? (TValue)Convert.ChangeType(1, underlying)!;
dynamic dc = c!;
dynamic ds = s!;
return subtract ? (TValue)(dc - ds) : (TValue)(dc + ds);
```

Alternatives rejected: (a) dispatch table with explicit casts for each of 22 types (verbose, error-prone), (b) expression trees (faster but adds compilation overhead per render). Dynamic dispatch is hot only on stepper button click — performance impact negligible for HIS use cases.

### 9.2 JS DOM value-sync (`lipiInput.setValue`)

In Batch 4.2 the C# input filter would strip non-numeric chars before parse. But Blazor's render diff sees `model.Value` unchanged after filter (parse failed, value didn't update), so it doesn't re-render the `<input>` element. The user-typed letter remained in the DOM.

Fix: imperative `lipiInput.setValue(input, value)` JS call after filter. Cursor preserved via `setSelectionRange(min(prevCursor, value.length))`. Tradeoff: range selection collapses to cursor (acceptable for numeric-input UX).

### 9.3 Dropdown JS architecture (Batch 5)

Four design calls in `lipi-input.js` for the LipiSelect/Combobox dropdown:

1. **`scroll` listener with `capture: true`** — scroll events don't bubble, but they DO propagate during the capture phase. Single document-level listener catches scroll on any scrollable ancestor (modal panels, scrollable containers, even the window).
2. **RAF-throttled reposition** — momentum scrolls fire scroll events at 60fps. Without throttling, `positionDropdown` runs 60×/second flooding the SignalR roundtrip. `requestAnimationFrame` collapses redundant invocations.
3. **`window._lipiSelectState[dropdownId]` namespacing** — multiple concurrent dropdowns must coexist without leaking listeners. Per-dropdown state (anchor ref, listeners, RAF id) keyed by the dropdown's element ID.
4. **Defensive detach-before-attach** — `attachSelectHandlers` calls `detachSelectHandlers` first. Protects against re-render double-attach during fast user interactions.

### 9.4 Reposition-don't-close on scroll (HIS-specific UX)

When the user scrolls while a dropdown is open, the dropdown REPOSITIONS to follow the anchor instead of closing. Material UI does this. Ant Design and React-Select close. Carbon repositions.

Reasoning: clinical workstations may have tracking pointers, accessibility scroll modes, or scrollable modal panels. Closing-on-scroll surprises the user mid-selection. Reposition is the safer default for HIS.

### 9.5 Pinned options sort preservation

`PinnedValues` is `IEnumerable<TValue>`. Pinned items render in the order the caller passed them — NOT alphabetical, NOT by `Items` order. After filtering by search text, pinned items retain caller order via `pinned.Sort((a, b) => pinnedOrder.IndexOf(a).CompareTo(pinnedOrder.IndexOf(b)))`.

Reasoning: caller knows the priority. "Recently used" might want most-recent first. "Common countries" might want India first because the deployment is Indian. Forcing alphabetical hides intent.

### 9.6 `TryParseValueFromString` triple cascade (selects)

Parse order:

1. **Label match** — search `Items` for `ItemLabel(item) == value` (case-insensitive). Most common path (user typed/picked from list).
2. **Value-string match** — search `Items` for `ItemValue(item).ToString() == value`. Edge case: user pasted the underlying value rather than the label.
3. **AllowFreeText fallback** — when `AllowFreeText=true`, accept the typed string as TValue via `BindConverter.TryConvertTo`. When false, parse fails with a user-readable validation message: `"X" is not a valid option for {DisplayName}.`

### 9.7 Form-orphan technique for search-input Enter

`<input form="lipi-select-orphan">` disassociates the dropdown's search input from any ancestor `<EditForm>`. Without this, pressing Enter to select an option would also submit the form (Blazor Server's async event roundtrip means our C# Enter handler runs AFTER the browser's default form submission).

Standard HTML5; supported Chrome 80+ / Firefox 30+ / Safari 12+ / Edge — covers all HIS deployments. Material UI's `<Autocomplete>` uses the same technique inside its Popper.

### 9.8 Full ARIA combobox/listbox/option pattern

The select family implements WAI-ARIA 1.2's combobox pattern:

- Anchor: `role="combobox"` + `aria-expanded` + `aria-controls` + `aria-haspopup="listbox"` + `tabindex="0"`
- Dropdown: `role="listbox"` + `aria-label="{Label} options"`
- Each option: `role="option"` + `aria-selected="true|false"`
- Search input: `role="searchbox"` (implicit via `<input type="text">`)

Screen readers announce: "{Label}, combo box, expanded, list of N options. {Highlighted option}, selected."

### 9.9 `EqualityComparer<TValue>.Default` for value comparison

All "is this option selected?" / "is this value pinned?" comparisons use `EqualityComparer<TValue?>.Default.Equals(a, b)`. Type-agnostic, handles nullable structs correctly, respects custom `IEquatable<T>` implementations on caller types (e.g., `record class Country : IEquatable<Country>`).

### 9.10 `IAsyncDisposable` for handler cleanup

`LipiSelectBase<TValue, TItem>` implements `IAsyncDisposable`. On disposal:

```csharp
await DetachJsHandlersAsync();   // Remove document-level event listeners
_dotNetRef?.Dispose();           // Release DotNetObjectReference
GC.SuppressFinalize(this);
```

Preventing `DotNetObjectReference` leaks is critical — Blazor circuits accumulate refs over time, eventually exhausting memory. Always dispose async refs explicitly.

### 9.11 Compound-vs-descendant CSS selector trap (Batch 5.4 lesson)

CSS selector form:

- **`.A .B .C`** (with spaces) — `.C` is a descendant of `.B` which is a descendant of `.A`. Three levels of DOM nesting required.
- **`.A.B .C`** (no space between A and B) — `.C` is a descendant of an element having BOTH classes `A` AND `B`. Two levels of DOM.

When two classes are applied to the SAME element (e.g., `<div class="lipi-input-medium lipi-input-select">`), the selector targeting both must use compound (no space) form. Descendant (with space) form will silently fail to match.

The Batch 5.4 bug was exactly this: `.lipi-input-medium .lipi-input-select .lipi-input-field` was looking for a `.lipi-input-select` nested inside `.lipi-input-medium`, but both were sibling classes on the same wrapper. Result: height rule never applied, field auto-sized to content (~17.6px instead of 32px).

**Lesson for future component CSS authors**: when an element receives multiple state-driven classes, target them with compound selectors (no spaces between class selectors). Descendant selectors are for ACTUAL DOM hierarchy.

## 10 — Known limitations

### 10.1 Unsigned `TValue` underflow without explicit `Min` (LipiNumberInput)

`LipiNumberInput<uint?>` with stepper button "−" pressed at value `0` will throw at `dynamic` arithmetic (uint underflow). Mitigation: pass `Min="0"` explicitly. The at-bound logic disables the "−" button when `value == Min`, preventing the underflow.

### 10.2 Multi-decimal-point silent stripping (LipiNumberInput)

The C# input filter handles only the first decimal separator per text. Pasting `1.2.3` yields `1.23` (subsequent separators stripped silently). User has no visual indicator.

Considered alternatives: (a) reject the paste entirely (worse UX), (b) flash a brief warning (adds JS+CSS surface). Decision: silent strip is acceptable for clinical-numeric inputs where multi-decimal pastes are user error, not malicious.

### 10.3 Composition events / IME / non-Latin numerals (LipiNumberInput)

The filter treats non-ASCII numerals (Devanagari `१२३`, Arabic `١٢٣`) as non-numeric and strips them. Workaround: callers needing Devanagari numeric input should set `BlockNonNumericInput="false"` and rely on parse-time conversion via culture-aware `BindConverter`.

IME composition events (Japanese / Chinese input) may briefly show partial composition state that the filter strips. Not blocking for v1.0 — Japanese / Chinese clinical deployments are post-v1.0.

### 10.4 Range selection collapses to cursor on filter (LipiNumberInput)

When the user selects a range in the input and types a non-numeric character, the filter strips the character AND the cursor collapses to a single position (start of the selection). The native browser behavior would have replaced the selected range. Consequence: minor, but visible.

Fix is non-trivial in `lipiInput.setValue` JS: would need to detect the range selection state pre-filter and restore it. Deferred.

### 10.5 Brief letter-flash on Blazor Server (BlockNonNumericInput)

The C# filter runs on `@oninput`, which round-trips to the server via SignalR before stripping the character. On a typical LAN (< 50ms) the user sees the unwanted character flash for ~20-60ms before the DOM update strips it. On WAN connections (> 200ms) this flash becomes more visible.

Mitigation paths considered:
- (a) Add a JS-side keypress filter that runs before the server roundtrip — adds JS surface and dual-validation complexity
- (b) Switch to `BlockNonNumericInput="false"` for high-latency deployments — defers validation to parse-time
- (c) Accept the flash for v1.0 — chosen path; revisit if PatientNew migration shows it's actually disruptive

Caller markup is now:

```razor
<LipiTextBox Name="firstName" @bind-Value="model.FirstName" />
@* No ValidationMessage needed — Error auto-populates from EditContext *@
```

Implementation: `LipiInputBase<TValue>` subscribes to `EditContext.OnValidationStateChanged` in `OnInitialized` (with swap-handling in `OnParametersSet`). On each event, it pulls the current first message for this component's `FieldIdentifier` via `EditContext.GetValidationMessages(FieldIdentifier).FirstOrDefault()` and assigns to `_editContextError`.

`EffectiveError` resolves to `Error ?? _editContextError` — caller-set `Error` takes precedence. The state precedence cascade (Disabled > ReadOnly > Error > Success > Warning > RequiredEmpty > Default) reads `EffectiveError` not `Error`, so EditContext-driven errors elevate state correctly.

The component exposes a touched-state pattern for "validate on first blur, then on input" UX (see §10.7 below).

### 10.7 Validation suppressed until first blur (intentional — UX pattern)

Validation messages do NOT appear in the helper slot until the user has blurred the field at least once. Per-keystroke validation noise (typing "v" → "Invalid email format" instantly) is bad UX; users want to type without the form yelling at them mid-word.

Implementation in `LipiInputBase<TValue>`: `_isTouched` bool flag, false until `HandleBlur` fires. In `HandleValidationStateChanged`, the error is gated on `_isTouched` — until first blur, `_editContextError` stays null regardless of what DataAnnotations would say.

Once blurred, every subsequent keystroke updates validation immediately. Matches Material UI / Carbon / Ant Design / every major form library. Microsoft's `InputBase<TValue>` does NOT do this — `LipiInputBase<TValue>` adds it at the family level.

**Side effect to be aware of**: empty fields tabbed past without typing must trigger validation too. `HandleBlur` calls `EditContext.NotifyFieldChanged(FieldIdentifier)` to force DataAnnotations to evaluate the field even when the value is empty/unchanged. Without this, `[Required]` on a never-typed field would never fire.

### 10.8 `[EmailAddress]` regex is permissive (.NET behavior, not a component limitation)

.NET's `[EmailAddress]` attribute uses a permissive regex that accepts `valid@e` (no TLD, single-character domain). For stricter email validation, callers should add `[RegularExpression]`:

```csharp
[Required]
[EmailAddress]
[RegularExpression(@"^[^@\s]+@[^@\s]+\.[^@\s]{2,}$",
    ErrorMessage = "Email must include a valid TLD")]
public string Email { get; set; }
```

We deliberately do NOT bake stricter email validation into `LipiTextBox` — international domains, plus-addressing, IPv6 literal hosts, and other valid edge cases get rejected by overly-strict regex. Caller opt-in via `[RegularExpression]` is the right escape hatch.

### 10.9 LipiTextBox does not block non-numeric input (use `LipiNumberInput` or `[RegularExpression]`)

`LipiTextBox` accepts any character. For digit-only fields like phone numbers, two paths:

1. **Validation-time rejection** (current recommended path):
   ```csharp
   [Required(ErrorMessage = "Mobile is required")]
   [RegularExpression(@"^\d{10}$", ErrorMessage = "Mobile must be 10 digits")]
   public string Mobile { get; set; }
   ```
   User can type letters; validation rejects on blur.

2. **Keystroke-level blocking** (Phase 2.3 enhancement, not 2.2.5 scope): a `BlockNonNumericInput` parameter on `LipiTextBox`, mirroring `LipiNumberInput`'s parameter of the same name. Phone numbers aren't really numbers (leading zeros, country codes, formatting) so `LipiNumberInput` is the wrong fit; `LipiTextBox` with a digit-only mode is the right fit.

`LipiNumberInput<TValue>` is the right choice for actual numeric values (lab measurements, counts, currency) — its filter is locale-aware and respects type bounds.

### 10.10 Caller-set `Error` displays but does NOT fail `EditContext.Validate()`

The `Error` parameter is for **display only**, not for blocking form submission. `EditContext.Validate()` returns `true` if all DataAnnotations pass — caller-set `Error` doesn't register as a validation error.

This is the intentional consequence of the locked decision "caller-set Error wins for display." For submission-blocking errors driven by external state (server-side validation, async checks), check the underlying state in your `OnValidSubmit` handler:

```csharp
private async Task OnValidSubmit()
{
    if (_simulateServerError) {
        _simulateServerError = false; // or keep set; the LipiTextBox Error parameter still displays
        return;
    }
    // ... actual submit logic
}
```

For a unified pattern that BOTH displays the error AND fails validation, callers can attach a custom validator that checks external state and registers messages with `EditContext.GetMessageStore().Add(...)`. This is a Phase 2.3 candidate for a `LipiServerValidationProvider` helper component.

## 11 — Migration guide (UsersNew worked example)

This section shows a concrete before/after for migrating one form field from the legacy `af-fgroup` / `af-finput` / manual-handler pattern to the InputBase + EditForm pattern.

### 11.1 Source: legacy UsersNew "First Name" field

```razor
<div class="af-fgroup">
    <label class="af-flabel" for="un-fn">
        First Name <span class="af-req">*</span>
    </label>
    <input id="un-fn"
           autocomplete="given-name"
           name="firstName"
           class="af-finput @ErrCss(FN)"
           value="@m.FirstName"
           @oninput="OnFirstNameInput"
           @onblur="OnFirstNameBlur"
           placeholder="Letters only" />
    @ErrSpan(FN)
</div>

@code {
    private const string FN = "fn";

    private void OnFirstNameInput(ChangeEventArgs e)
    {
        m.FirstName = e.Value?.ToString() ?? string.Empty;
        if (_dirty.Contains(FN)) ValidateFn();
    }

    private void OnFirstNameBlur()
    {
        _dirty.Add(FN);
        ValidateFn();
    }

    private void ValidateFn()
    {
        if (string.IsNullOrWhiteSpace(m.FirstName))
            _errors[FN] = "First name is required";
        else if (!Regex.IsMatch(m.FirstName, @"^[a-zA-Z\s]+$"))
            _errors[FN] = "Letters only";
        else
            _errors.Remove(FN);
    }
}
```

This is **42 lines per field** for one validated input: markup + 3 handlers + state-tracking dictionary. Multiplied across 30+ fields in PatientNew and UsersNew, it adds up.

### 11.2 Target: LipiTextBox + DataAnnotations

**Step 1**: add validation attributes to the model.

```csharp
public class UsersNewModel
{
    [Required(ErrorMessage = "First name is required")]
    [RegularExpression(@"^[a-zA-Z\s]+$", ErrorMessage = "Letters only")]
    public string FirstName { get; set; } = string.Empty;

    // ...
}
```

**Step 2**: replace the field markup.

```razor
<EditForm Model="m" OnValidSubmit="OnSubmit" OnInvalidSubmit="OnInvalidSubmit">
    <DataAnnotationsValidator />

    <LipiTextBox Name="firstName"
                 Label="First Name"
                 Required="true"
                 Autocomplete="given-name"
                 Placeholder="Letters only"
                 @bind-Value="m.FirstName" />
    <ValidationMessage For="@(() => m.FirstName)" />

    <!-- ... other fields ... -->

    <LipiButton Variant="ButtonVariant.Primary" Type="submit" Icon="save">
        Register User
    </LipiButton>
</EditForm>
```

**Step 3**: delete the manual handlers and dictionary state.

The result: **8 lines per field** (markup) + 3 lines on the model. No handlers, no dictionary, no `ErrCss` / `ErrSpan` helper methods. 5× reduction in per-field code volume.

### 11.3 What you GAIN with the migration

- ✅ Apricot tint on empty required (free, automatic)
- ✅ State precedence cascade — no manual error-vs-warning conflict logic
- ✅ Confidence pills (when applicable, e.g., DOB on patient forms)
- ✅ Locale-aware numeric formatting (LipiNumberInput on Age, BMI, etc.)
- ✅ Form-orphan-free dropdown Enter handling (LipiSelect inside EditForm just works)
- ✅ Valid HTML5 autocomplete tokens (validator catches `country-name` typo at component-instantiation)
- ✅ Accessibility: ARIA attributes, helper-text association, focus-ring management

### 11.4 What you LOSE (or trade off)

- ❌ Custom inline validation messages per-keystroke (e.g., showing required-asterisk-only when blur, then full-message on input). Phase 2.2 components show error from the `Error` parameter or `ValidationMessage<For>` — both fire on form-level events, not individual keystrokes. Phase 2.2.5 may add per-component blur-vs-input controls.
- ❌ Bespoke field background colors. The state cascade owns the field background. If a caller wants a bespoke "blue tinted on focus" pattern outside the cascade, they need a custom variant.
- ❌ Direct DOM manipulation in `@onkeydown`. Custom keystroke handlers are still possible via `@onkeydown` on the wrapping element, but interfering with the component's internal handlers (e.g., for LipiSelect arrow keys) requires care.

### 11.5 Recommended migration order

1. **Login + OTP forms first** — small, low-risk, exercises LipiTextBox in isolation
2. **Settings + UsersNew + UsersEdit** — medium complexity, exercises all 5 components, high test coverage
3. **ClinicsNew + OrgsNew** — similar to Users but with file-upload handling outside scope
4. **PatientNew last** — most complex (30+ fields, sections, conditional logic). Migration is highest-value but highest-risk; saves the learnings from steps 1-3.

Phase 2.2.5 (validation auto-population) is a prerequisite for full PatientNew migration — without it, every field needs an explicit `<ValidationMessage>` next to it which is verbose.
