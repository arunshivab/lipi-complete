# Phase 2.10 — Infrastructure Audit Checklist

> **Status**: Living list. Items append as work surfaces them; nothing
> deletes without an entry in `CHANGE-LOG.md`.
> **Audit phase position**: After Phase 2.8 (Data Display) and Phase 2.9
> (Navigation) close; **HARD GATE before page-redesign work begins**.
> **Last updated**: 2026-05-15 (A36 — Phase 2.7 close-out consolidation)

## Purpose

This doc is the single source of truth for what the Phase 2.10
Infrastructure Audit must address. Anything queued for 2.10 — whether
from the locked roadmap, surfaced during component-library builds, or
flagged by other audits — lands here.

The audit chat works from this list. Items can be:
- **Fixed** (audit makes the change, ships it, updates this doc)
- **Deferred** (decision made to push to v1.1+; documented in CHANGE-LOG;
  removed from this list)
- **Confirmed as-is** (audit reviews and decides v1.0 state is correct;
  documented in CHANGE-LOG; removed from this list)

Each item below carries: **severity**, **source** (phase / decision where
it was surfaced), **v1.0 state** (what's deployed today), **audit action**
(what the audit needs to do), **files affected**, and **rationale** (why
this isn't blocking v1.0).

## Severity legend

- **High**: Production safety, HIPAA compliance, or security implications.
  Must be addressed before page redesign.
- **Medium**: Architecture consistency, technical debt that compounds if
  ignored. Should be addressed in 2.10.
- **Low**: Documentation, naming, or convention. Can defer to v1.1 if 2.10
  scope grows.

## A — LOCKED scope (from project roadmap / baseline)

These were locked into Phase 2.10 before component-library work began.

### Item A1 — Cross-page nav scoped-CSS smoke test

**Severity**: Medium
**Source**: Phase 2.6 cross-link pattern (`data-enhance-nav="false"`)

**v1.0 state**: Phase 2.6 introduced `data-enhance-nav="false"` on the
StyleGuide cross-page links because Blazor enhanced navigation streams a
partial body swap that does NOT reattach the scoped CSS bundle
(`LiPi.Web.styles.css`). Without the attribute, destination pages render
unstyled until `Ctrl+Shift+R`. The attribute is on StyleGuide demo links
only.

**Audit action**: Smoke test every cross-page nav in the app (not just
StyleGuide demos). Confirm production pages aren't affected because they
depend on global CSS (`admin.css`, etc.) more than scoped `.razor.css`,
which is the working hypothesis but unverified. If any production page
breaks, decide between (a) blanket-disable enhanced nav, (b) selectively
add `data-enhance-nav="false"`, or (c) the proper Blazor 8/9/10 fix
(consult release notes).

**Files affected**: Every `<a>` element with internal href in the entire
codebase. Smoke test script lives outside this doc.

**Rationale**: Production-page safety is unverified, but the symptom
(unstyled page until hard refresh) is cosmetic, not data-corrupting.
Acceptable to defer v1.0 launch behind 2.10's verification.


### Item A2 — Component package isolation audit

**Severity**: Medium
**Source**: Project memory rule — "LiPi component library must be
designed as a standalone redistributable package for any Blazor app."

**v1.0 state**: All LiPi components (Phase 2.1 – 2.7) are designed to
this standard, but isolation hasn't been audited in one sweep. Strict
requirements: no HIS-specific names, routes, or services; CSS uses
`lipi-*` prefix only (never `reg-*` / `ue-*` / `cn-*`); CSS depends only
on the documented token contract (`--color-*`, `--sp-*`, `--r-*`);
components inject only `Microsoft.*` / `LiPi.*` generics — never
HIS-specific services.

**Audit action**: Grep every `LiPi.Web.Components.Shared/Lipi*` file for
violations. Report each violation with file:line and suggested fix.
Flag any CSS rules using non-standard tokens or hardcoded colors. Flag
any component injecting an HIS-specific service.

**Files affected**: All files under
`src/LiPi.Web/Components/Shared/Lipi*.razor` and `.razor.cs` and
`.razor.css` and the corresponding `Lipi*Types.cs`. Also
`src/LiPi.Web/wwwroot/css/lipi-*.css`.

**Rationale**: Isolation violations don't break v1.0 functionality but
prevent the library from being lifted into a future product cleanly.


### Item A3 — Remove legacy `AddServerSideBlazor()` from Program.cs

**Severity**: High (touches Blazor app bootstrap)
**Source**: Project memory — known .NET 7 legacy pattern; carried
forward through phase work because removing without migration breaks
events.

**v1.0 state**: Program.cs still contains
`builder.Services.AddServerSideBlazor().AddCircuitOptions(o =>
o.DetailedErrors = true)`. This is the .NET 7 / Blazor Server bootstrap
pattern. .NET 8+ Blazor Web App uses
`AddRazorComponents().AddInteractiveServerComponents()` instead.
Removing the legacy line without the migration breaks interactive
circuits app-wide.

**Audit action**: Plan the migration: identify how `DetailedErrors` is
preserved under the new bootstrap (the `AddInteractiveServerComponents`
overload accepts a similar options delegate); confirm any other circuit
options in current use; test in a branch before merging. Once verified,
remove the legacy line.

**Files affected**: `src/LiPi.Web/Program.cs`. No other source files
should reference `AddServerSideBlazor`.

**Rationale**: Functional today. Migration is purely about removing the
legacy bootstrap line cleanly without taking down events.


### Item A4 — PHI access log + audit events HIPAA gap closure

**Severity**: High (compliance)
**Source**: Project standing rule — HIPAA on every feature.

**v1.0 state**: `IAuditService` and `AuditActions` constants exist and
are used in admin flows. PHI access logging (every read/write of patient
data) is NOT comprehensively wired. The Patient Registration module
(Phase 4) has partial coverage; other clinic modules vary.

**Audit action**: Inventory every entity-level operation across all
modules. Confirm each PHI access produces an audit event with
before_state + after_state where applicable. Add coverage where missing.
Audit retention (immutable append-only? blockchain anchored? per the
locked decisions) confirmed.

**Files affected**: Every page under
`src/LiPi.Web/Pages/Patients/`, `src/LiPi.Web/Pages/Admin/`, plus every
EF Core entity write path. `AuditService.cs` may need extension.

**Rationale**: HIPAA gap closure can happen in the audit phase because
component-library work doesn't directly touch PHI access paths. Page
redesign work, however, will touch PHI paths heavily — close the gap
BEFORE redesign starts.

### Item C1 — `--color-danger-text-strong` hex collides with `--color-danger-active`

**Severity**: Low
**Source**: Phase 2.7 token additions (A35).

**v1.0 state**: Both tokens resolve to `#991B1B` in light mode. Two
different semantic roles (text-on-tinted-bg vs button-active-fill) share
one hex. Documented dependency.

**Audit action**: Decide whether to (a) keep the collision and treat the
hex as a deliberate shared anchor across roles, or (b) split the values
(e.g., `--color-danger-text-strong: #991B1B`, `--color-danger-active:
#7F1D1D`) for independent evolution.

**Files affected**: `src/LiPi.Web/wwwroot/themes/mode-light.css`,
`mode-dark.css`.

**Rationale**: Either choice is fine; v1.0 ships with the collision
because both roles happen to want the same value today.


### Item C2 — Spec→deployed token name mapping (9 divergences)

**Severity**: Medium
**Source**: Phase 2.7 build — A35 mapping table.

**v1.0 state**: Phase 2.7 specs use token names that diverge from the
deployed set (e.g., `--color-success-fill` in spec vs `--color-success`
deployed; full table in A35). Component CSS uses deployed names; each
file's header comment documents the divergence.

**Audit action**: Decide whether to rename deployed tokens to match
specs (cheaper for new component authors, breaks all existing CSS) or
rewrite specs to use deployed names (cheaper for existing code, every
spec needs updating). Document the canonical naming convention going
forward.

**Files affected**: All Phase 2.7 spec docs under
`docs/00-COMPONENTS/2.7/` OR all theme files +
all `lipi-*.css` files.

**Rationale**: Either direction is fine; v1.0 ships with the divergence
documented and components working correctly because they reference the
deployed names.


### Item C3 — `LipiToastHost` inline `<style>` block

**Severity**: Low
**Source**: Phase 2.7 build — A35.

**v1.0 state**: `LipiToastHost.razor` contains an inline `<style>` block
with the 6 corner-positioning rules, rather than a separate `.razor.css`
or `wwwroot/css/lipi-toast-host.css` file. Decision rationale: host is a
singleton in TopNavLayout, positions are short and well-defined, and a
separate file would add a deploy-script entry for ~30 lines of layout
CSS.

**Audit action**: Confirm the inline-style approach is acceptable for
singleton host components OR migrate to a separate file if a project
convention emerges that disallows inline styles.

**Files affected**: `src/LiPi.Web/Components/Shared/LipiToastHost.razor`
(possibly extract to a new sibling `.razor.css`).

**Rationale**: Functional today. Convention question only.

### Item C5 — LipiValidationSummary object-level EditContext errors

**Severity**: Low
**Source**: Phase 2.7 build (A35 locked design decision; A36 promoted
to explicit Phase 2.10 audit item).

**v1.0 state**: `LipiValidationSummary` auto-discovers errors from
`EditContext` for field-level rules. Object-level errors (errors whose
`FieldIdentifier.FieldName == ""`) are NOT auto-discovered, because
`EditContext`'s public API doesn't cleanly expose object-level
`FieldIdentifier` without reflection that risks breaking on framework
upgrades. Consumers with object-level rules supply `Errors` explicitly
via the parameter (with `FieldName = "*"` convention).

**Audit action**: Either (a) accept as a permanent v1.0+ limitation
documented in the spec, or (b) implement reflection-based discovery
with explicit framework-version guards. The reflection approach lets
object-level rules flow through `EditContext` without manual wiring.

**Files affected**:
`src/LiPi.Web/Components/Shared/LipiValidationSummary.razor.cs`,
spec `docs/00-COMPONENTS/2.7/04-LipiValidationSummary-Spec.md`.

**Rationale**: Field-level rules cover 95%+ of real forms. v1.0 ships
without object-level auto-discovery and is fine for the patient
registration, settings, and admin forms in scope.


### Item C6 — Blazor CSS Isolation: every new `StyleGuide*.razor` page needs standalone `sg-*` base

**Severity**: Medium
**Source**: Phase 2.7 build — Bug 2 fix (A36 capture).

**v1.0 state**: Blazor CSS Isolation appends a per-component scope
attribute (e.g. `[b-abc123]`) to every selector defined in a
`.razor.css` file and to every element rendered by the corresponding
`.razor` file. Rules defined in one component's `.razor.css` do NOT
apply to elements rendered by another component, even when both use the
same class name. The initial Phase 2.7 `StyleGuideFeedback.razor.css`
assumed inheritance from `StyleGuide.razor.css` and shipped broken
(sidebar collapsed, demo numbers running into text). Fixed by porting
the full base `sg-*` rule block, matching the
`StyleGuideOverlays.razor.css` pattern.

**Audit action**: Document this pattern in
`docs/00-COMPONENTS/00.2-THEMING-ARCHITECTURE.md` (or a new
`Component-Authoring-Conventions.md`) so future StyleGuide pages don't
hit the same bug. Optional: extract the shared `sg-*` base block to a
real wwwroot CSS file (`lipi-styleguide.css`) and have all StyleGuide
pages import it instead of duplicating, so the pattern is enforced by
inclusion rather than convention.

**Files affected**: Convention only:
`docs/00-COMPONENTS/00.2-THEMING-ARCHITECTURE.md` or a new doc.
If extracted: new `src/LiPi.Web/wwwroot/css/lipi-styleguide.css` +
all `StyleGuide*.razor.css` files simplified.

**Rationale**: One-time pattern documentation. Without it, every new
StyleGuide page risks the same bug. The fix is in production for
`StyleGuideFeedback`; this audit item makes the lesson durable.


### Item C7 — Host-component rendermode: every singleton service-driven renderer in a layout needs `@rendermode InteractiveServer`

**Severity**: High (silent failure — toast / overlay does nothing
visible, no error)
**Source**: Phase 2.7 build — Bug 3 fix (A36 capture).

**v1.0 state**: `LipiToastHost.razor` initially shipped without
`@rendermode InteractiveServer`. The host rendered SSR-only on first
paint, subscribed to `ILipiToastService.OnChanged` in the SSR pass, and
that subscription was dead by the time the interactive circuit
attached. When pages called `_toast.Success(...)`, nothing rendered.
Silent failure with no console or server error. Fixed by adding the
directive. `LipiOverlayHost.razor` had it from the start (which is why
modals always worked).

**Audit action**: Document this pattern in
`docs/00-COMPONENTS/00.2-THEMING-ARCHITECTURE.md` or a new
`Component-Authoring-Conventions.md`. Specifically: **any component
that subscribes to a Scoped service event in `OnInitialized` AND is
mounted in a layout (not a page) MUST have
`@rendermode InteractiveServer` at the top.** Convention should be
verified by checklist for every future host-pattern component.

**Files affected**: Convention only.
Concrete: `LipiOverlayHost.razor` (already correct),
`LipiToastHost.razor` (fixed in A36 build). Any future hosts (e.g., a
hypothetical `LipiNotificationCenterHost`) covered by the convention.

**Rationale**: Silent failure mode is the worst kind of bug —
unrelenting symptom ("doesn't work") with no diagnostic trail. Pattern
documentation prevents the next host from shipping broken.
