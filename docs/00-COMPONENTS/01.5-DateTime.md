## Components covered

| Component | Generic | Bind type | Use case | Sub-step |
|-----------|---------|-----------|----------|----------|
| `LipiDatePicker` | no | `DateOnly?` | Single date — DOB, appointment date, document date | 2.4 / Batch 9d |

`DateSegment` was originally specified as a separate segment for `LipiCompoundField`. It was absorbed as `InputMode=Segments` of `LipiDatePicker` (decision F3) — a single component with two render modes is simpler than a separate segment type that duplicates calendar-popover wiring.

The `LabelConfidence` parameter on `LipiDatePicker` already supports the visual pill; the dedicated DOB picker would add domain-specific UX patterns (override flow, audit trail).

## 1 — Architecture

### 1.1 Class hierarchy

```
                ComponentBase
                    │
        ┌───────────┴────────────┐
        │                        │
  InputBase<TValue>      ComponentBase (direct)
        │                        │
  LipiInputBase<TValue>     LipiDateRangePicker
        │                   (dual StartValue + EndValue —
        │                    no single TValue, no
        │                    LipiInputBase derivation)
        │
        ├── LipiDatePicker        (TValue=DateOnly?)
        ├── LipiTimePicker        (TValue=TimeOnly?)
        └── LipiDateTimePicker    (TValue=DateTimeOffset?)
```

Three of the four components inherit `LipiInputBase` and participate in `EditForm` validation, EditContext subscription, the touched-state model, and the family visual cascade. `LipiDateRangePicker` is the architectural exception — its dual-value binding shape (separate `StartValue` + `EndValue`) doesn't fit the single-TValue mold. It re-implements the visual scaffolding inline.

### 1.2 Service dependencies

Two new services support the Date/Time family:

- `IDateFormatService` — clinic-configurable date and time format (parse + format + segment order)
- `IClinicTimezoneService` — clinic timezone resolution (NOT system clock)

Both are registered as scoped services in `Program.cs`:

```csharp
builder.Services.AddScoped<IDateFormatService, DateFormatService>();
builder.Services.AddScoped<IClinicTimezoneService, ClinicTimezoneService>();
```

The Phase 2.4 default implementations hardcode India defaults. When the clinic-config schema lands (master.clinics gains `date_format` / `time_format` / `week_start_day` / `timezone_id` columns), the service implementations read from clinic context without consumer changes.

### 1.3 Storage vs display formats

**Database storage** is always ISO 8601 (decision A1):
- `DateOnly` → PostgreSQL `DATE` column
- `TimeOnly` → PostgreSQL `TIME` column
- `DateTimeOffset` → PostgreSQL `TIMESTAMPTZ` column

**Display** is configurable per clinic (default DD/MM/YYYY for India). Components ALWAYS round-trip through the format service for display + parse; raw `ToString()` is never used.

### 1.4 Time provenance

For most timestamps, a single TIMESTAMPTZ column is sufficient. For external-source captures (e.g., timestamps imported from lab systems where the source's clock may differ from the clinic's), an additional `_source` column should be added. For forensically critical timestamps (rare), a triple-column pattern (`_utc` + `_tz_id` + `_source`) preserves full provenance. Phase 2.4 components don't enforce this — provenance is an integration-layer concern. See design package §2.3.

## 2 — Cross-cutting behaviors (all components)

### 2.1 Format library

Format strings use uppercase tokens for clarity (the user-facing `master.clinics.date_format` config column will hold these strings):

| Token | Meaning | Example |
|-------|---------|---------|
| `D` | Day, no leading zero | 1, 2, ..., 31 |
| `DD` | Day, leading zero | 01, 02, ..., 31 |
| `M` | Month, no leading zero | 1, 2, ..., 12 |
| `MM` | Month, leading zero | 01, 02, ..., 12 |
| `MMM` | Month abbreviation | Jan, Feb, ..., Dec |
| `MMMM` | Month full name | January, February, ..., December |
| `YY` | Year, 2-digit | 24, 25, 26 |
| `YYYY` | Year, 4-digit | 2024, 2025, 2026 |

Separators: `/`, `-`, `.`, space. The 12 explicitly supported combinations are listed in `DateFormatService.cs`.

For segment input (`LipiDatePicker InputMode=Segments`), word-month formats (MMM, MMMM) collapse to numeric `MM` for the input phase — display can still use the rich format. This is a deliberate constraint: typing month names into a segmented input is too error-prone.

### 2.2 Clinic timezone

`IClinicTimezoneService` resolves the current clinic's timezone. Phase 2.4 hardcodes "Asia/Kolkata" (UTC+5:30, no DST). All composition of `DateOnly + TimeOnly → DateTimeOffset` (in `LipiDateTimePicker`) goes through this service for the offset.

**India + DST**: India does NOT observe DST. The country-wide IST offset is constant +05:30. This means `LipiDateTimePicker` has unambiguous semantics in India — no fall-back hour, no spring-forward hour. For DST-observing zones, the composition has known ambiguity gaps documented in CHANGE-LOG A20 as a v1.1 international-expansion concern.

### 2.3 Date constraints (4 predicates)

All date components support the same constraint cascade:

- `MinDate (DateOnly?)` — earliest selectable date (inclusive)
- `MaxDate (DateOnly?)` — latest selectable date (inclusive)
- `IsDateAllowed (Func<DateOnly, bool>?)` — custom predicate; returns `false` → disabled
- `IsDateDisabled (Func<DateOnly, bool>?)` — blackout predicate; returns `true` → disabled
- `GetDisabledReason (Func<DateOnly, string?>?)` — companion to `IsDateDisabled` for tooltip

**`IsDateAllowed` vs `IsDateDisabled`** — semantic distinction:

- `IsDateAllowed=false`: "this date doesn't satisfy the constraint" (e.g., weekends only).
- `IsDateDisabled=true`: "this date is temporarily unavailable for an explainable reason" (e.g., holiday, outage). Pairs with `GetDisabledReason` for hover text.

**`GetDisabledReason` null fallback** (Flag 6 A6 lock):

If `IsDateDisabled` returns `true` but `GetDisabledReason` returns `null` or empty string, the disabled cell still shows a tooltip with the fallback text "Date unavailable". Empty tooltip on a disabled cell is never rendered.

### 2.4 Popover positioning

Calendar popovers (LipiDatePicker, LipiDateRangePicker) use `position: fixed` with JS-calculated viewport coordinates (decision A2.2 corrected). The `window.lipiDatePicker` JS module provides:

- `positionPopover(anchor, popover)` — initial placement with edge-aware flip up/down
- `attachReposition(anchor, popover)` — scroll/resize listeners (rAF-throttled)
- `detachReposition(popover)` — cleanup on close
- `focusElement(el)` — focus + select-all helper

`position: fixed` escapes ancestor `overflow:hidden` naturally, including modal containers. Known gotcha: ancestors with `transform`, `filter`, or `will-change` create new containing blocks that constrain `position:fixed`. None currently exist in LiPi; flag if introduced.

This matches the LipiSelect dropdown pattern (Phase 2.2 Batch 5) — same JS-driven positioning approach, no portal repatriation.

### 2.5 Mobile responsive

All popover-based components collapse to a centered overlay below 640px viewport via CSS `@media` query. The popover stays at `position: fixed` but with full-viewport top/left/right/bottom resets and flexbox centering. Touch targets ≥40px on mobile day cells.

### 2.6 Cell visualization cascade

Day cells in calendar grids respect this cascade:

```
disabled > selected/range-start/range-end > in-range > today > other-month > default
```

Disabled cells render with strikethrough + grayed text + non-interactive cursor. Selected cells get a solid filled circle. Today cells get an outlined circle (or empty if not selected). In-range cells (`LipiDateRangePicker` only) get a continuous light-blue background bar between start and end.

## 3 — `LipiDatePicker`

Single date picker bound to `DateOnly?`. Inherits `LipiInputBase<DateOnly?>`.

### 3.1 Parameters

Common parameters from `LipiInputBase` (Name, Label, Helper, Required, Disabled, ReadOnly, Size, etc.) plus:

| Parameter | Type | Default | Notes |
|-----------|------|---------|-------|
| `InputMode` | `DatePickerInputMode` | `Field` | `Field` = single text input; `Segments` = compound numeric segments |
| `Format` | `string?` | clinic default | Override the clinic's `GetClinicDateFormat()` for this instance |
| `MinDate` | `DateOnly?` | `null` | Earliest selectable; clamps year dropdown range |
| `MaxDate` | `DateOnly?` | `null` | Latest selectable; clamps year dropdown range |
| `IsDateAllowed` | `Func<DateOnly, bool>?` | `null` | Custom predicate for selectable dates |
| `IsDateDisabled` | `Func<DateOnly, bool>?` | `null` | Predicate for blackout dates |
| `GetDisabledReason` | `Func<DateOnly, string?>?` | `null` | Tooltip text companion to `IsDateDisabled` |

### 3.2 InputMode=Field (default)

Single text input with calendar icon. User types DD/MM/YYYY directly OR clicks the icon to open the popover. On blur, the typed text is parsed via `IDateFormatService.ParseDate`. Parse failures surface as validation errors via EditContext.

```razor
<LipiDatePicker Name="dob"
                Label="Date of Birth"
                @bind-Value="_model.Dob"
                Required="true"
                MaxDate="@DateOnly.FromDateTime(DateTime.Today)" />
```

### 3.3 InputMode=Segments

Three numeric segments (DD, MM, YYYY for India default — order from `IDateFormatService.GetSegmentOrder()`). Smart auto-advance on segment fill (γ lock — Flag 6 F2 correction):

- Type 2 digits in DD → focus jumps to MM with cursor at position 0
- Type 2 digits in MM → focus jumps to YYYY
- Type 4 digits in YYYY → completes (no further auto-advance from last segment)

Calendar icon also present for popover access. Backspace at empty segment focuses previous segment (UX nicety — JUDGMENT, not in strict spec).

```razor
<LipiDatePicker Name="appt"
                Label="Appointment date"
                InputMode="DatePickerInputMode.Segments"
                @bind-Value="_model.Appointment" />
```

### 3.4 Calendar popover

Compact layout. Header: prev arrow / Month dropdown / Year dropdown / next arrow. 7-column grid with up to 6 rows. Footer has only a Today button (auto-commits on click). Year dropdown range derived from `MinDate.Year..MaxDate.Year` if both set, otherwise ±50 years from today.

Click any cell = commits the date + closes the popover. No OK/Cancel toggle.

### 3.5 Keyboard navigation (B5 lock — full WAI-ARIA)

When the calendar popover is open and focused:

| Key | Behavior |
|-----|----------|
| `ArrowLeft / ArrowRight` | ±1 day |
| `ArrowUp / ArrowDown` | ±7 days (one week) |
| `PageUp / PageDown` | ±1 month |
| `Shift+PageUp / Shift+PageDown` | ±1 year |
| `Home / End` | First / last day of week (respecting clinic week start) |
| `Ctrl+Home / Ctrl+End` | First / last day of month |
| `Enter / Space` | Commit highlighted date |
| `Escape` | Close popover |

When focus is in the field (Field mode) or any segment (Segments mode), `ArrowDown` opens the popover. Highlighted cell is clamped to MinDate/MaxDate; if highlight moves outside the current display month, the display month auto-advances.

### 3.6 Validation flow

`TryParseValueFromString` defers to `IDateFormatService.ParseDate`. Parse failures set EditContext error message: "The {field} must be a valid date in format {DD/MM/YYYY}." Constraint violations (MinDate, MaxDate) are caught at cell-disable time (cells render disabled, click is no-op) — they don't fire EditContext errors, since the user can't pick them in the first place.

For Segments mode, partial input (some segments empty) does NOT clear `CurrentValue`. The last successfully parsed value is preserved until full re-entry — JUDGMENT call to avoid surprising data loss mid-edit.

## 4 — `LipiTimePicker`

Time-of-day picker bound to `TimeOnly?`. No popover. Pure segmented layout.

### 4.1 Parameters

Common parameters from `LipiInputBase` plus:

| Parameter | Type | Default | Notes |
|-----------|------|---------|-------|
| `TimeFormat` | `string?` | clinic default | `"12h"`, `"24h"`, or `null` (uses clinic) |
| `Step` | `int` | `1` | Minute step. User input violating step REJECTS; Now button SNAPS |
| `ShowNow` | `bool` | `true` | Whether the Now button is visible |

### 4.2 Format modes

**24h mode (default for India):** 2 numeric segments — `HH MM`. Hour 0-23, minute 0-59.

**12h mode:** 2 numeric segments + 1 AM/PM `<select>` — `HH MM AM/PM`. Hour 1-12 (12-hour convention).

```razor
<LipiTimePicker Name="appt-time"
                Label="Appointment slot"
                TimeFormat="12h"
                Step="15"
                @bind-Value="_model.AppointmentTime" />
```

### 4.3 Step validation (asymmetric — Flag 6 C2 lock)

The Step parameter behaves DIFFERENTLY for user input vs the Now button. **This asymmetry is deliberate:**

- **User-typed input** that violates Step → REJECT with error in helper slot. Value is NEVER silently mutated. Example: Step=15, user types `09:23` → on blur, error: "Time must be in 15-minute increments".
- **Now button** → SNAP to nearest past Step boundary. User sees the result and can edit. Example: Step=15, current time 09:23 → Now sets to 09:15.

The asymmetry expresses different intent semantics: user input represents explicit intent that should not be silently changed; Now is "fill in current moment, snapped to valid" which IS the intent.

### 4.4 Keyboard

| Key (in HH segment) | Behavior |
|---------------------|----------|
| `ArrowUp / ArrowDown` | Increment/decrement hour (wraps at boundary) |

| Key (in MM segment) | Behavior |
|---------------------|----------|
| `ArrowUp / ArrowDown` | Increment/decrement by `Step` (wraps at 60) |

| Key (in AM/PM select, 12h mode) | Behavior |
|--------------------------------|----------|
| `ArrowUp / ArrowDown` | Toggle AM ↔ PM |

### 4.5 Now button

Reads `IClinicTimezoneService.GetClinicLocalNow()` (NOT `DateTime.Now` — clinic timezone, not server timezone). Snaps to Step. Sets value, fires ValueChanged, marks field as touched.

## 5 — `LipiDateTimePicker`

Composite picker bound to `DateTimeOffset?`. Composes `LipiDatePicker` + `LipiTimePicker` internally.

### 5.1 Parameters

| Parameter | Type | Default | Notes |
|-----------|------|---------|-------|
| `Layout` | `DateTimeLayout` | `Stacked` | `Stacked` = vertical, `Inline` = horizontal (collapses to Stacked at <640px) |
| `DateFormat` | `string?` | clinic default | Pass-through to inner LipiDatePicker |
| `TimeFormat` | `string?` | clinic default | Pass-through to inner LipiTimePicker |
| `Step` | `int` | `1` | Pass-through to inner LipiTimePicker |
| `MinDate / MaxDate / IsDateAllowed / IsDateDisabled / GetDisabledReason` | (various) | — | Pass-through to inner LipiDatePicker |
| `ShowNow` | `bool` | `true` | Combined Now button (sets BOTH date and time) |

### 5.2 Composition pattern

Internal `_dateValue (DateOnly?)` + `_timeValue (TimeOnly?)`. When both are set, composed into `DateTimeOffset` using `IClinicTimezoneService` for the offset:

```csharp
var local = new DateTime(year, month, day, hour, minute, 0, DateTimeKind.Unspecified);
CurrentValue = ClinicTz.ToUtc(local);
```

For India, `ToUtc` produces `+05:30` offset always (no DST). For DST zones, the wall-clock-to-UTC conversion has ambiguity gaps in fall-back hours; v1.1 will add explicit ambiguity handling.

### 5.3 Coordination (D2 lock)

- **D2.1 Auto-focus**: After date pick, focus jumps to time HH segment IF time is empty. Currently relies on natural Tab order — explicit cross-component focus would require LipiTimePicker to expose a `FocusFirstSegmentAsync` method. Deferred unless real-world UX surfaces a gap.
- **D2.2 Now button** (decision lock): ALWAYS sets today's date AND current time. "Now means Now." No state-dependent logic.
- **D2.3 No combined popover**: separate UIs, smart coordination. The two pickers each have their own popover/segment lifecycle.

### 5.4 Sequential entry pattern

Time field is DISABLED until a date is set. User must pick date first; picking time before date is meaningless (would default to "today" silently — unintuitive).

### 5.5 Layout

**Stacked (default):** Date on top, Time below, Now button below time. Best for narrow forms.

**Inline:** Date left, Time right, Now button right of time. Auto-collapses to Stacked at <640px viewport via CSS `@media`.

## 6 — `LipiDateRangePicker`

Date range picker with separate `StartValue` + `EndValue` bindings. Inherits `ComponentBase` directly (NOT `LipiInputBase` — dual-value shape).

### 6.1 Parameters

| Parameter | Type | Default | Notes |
|-----------|------|---------|-------|
| `Name` | `string` | — | REQUIRED |
| `Label` | `string?` | — | Visible label |
| `StartValue` | `DateOnly?` | — | Bind via `@bind-StartValue` |
| `EndValue` | `DateOnly?` | — | Bind via `@bind-EndValue` |
| `Format` | `string?` | clinic default | Display format |
| `MinDate / MaxDate / IsDateAllowed / IsDateDisabled / GetDisabledReason` | (various) | — | Same as LipiDatePicker |
| `AllowOpenEnd` | `bool` | `false` | When true, EndValue can be left null (ongoing) |
| `Presets` | `List<DateRangePreset>?` | `null` | Optional preset panel |
| `Required / Disabled / ReadOnly / HelperText / Size / Class` | (various) | — | Standard parameters |

### 6.2 Dual-value binding (E1 lock)

Caller binds two SEPARATE properties, not a single composite:

```razor
<LipiDateRangePicker Name="period"
                     Label="Reporting period"
                     @bind-StartValue="_model.PeriodStart"
                     @bind-EndValue="_model.PeriodEnd" />
```

This matches database storage shape (`start_date` + `end_date` columns) and avoids forcing callers to invent a synthetic composite type. The component handles the picking-state machine internally; callers get the final values via the two changed callbacks.

### 6.3 Two-calendar popover

Left calendar shows `_displayMonth`, right calendar shows `_displayMonth + 1`. Both share the prev/next arrows (left calendar has prev, right has next). Click 1 = staged start. Click 2 = staged end (or swap if before start).

Mobile (<640px): single calendar, sequential picking. Right calendar hidden via CSS.

### 6.4 Range visualization (E3 lock)

- **Start cell**: solid blue circle, left-rounded corners
- **End cell**: solid blue circle, right-rounded corners
- **Single-day range** (start == end): full circle
- **In-range cells**: continuous light-blue background bar (no rounded corners — flush)
- **Hover preview**: dashed background while user is selecting end

### 6.5 Presets (E2 lock)

`LipiDateRangePresets` static class provides 12 individual presets:

```
Today, Yesterday, Tomorrow,
Last7Days, Last30Days, Next7Days, Next30Days,
NextWeek, NextMonth, ThisMonth, LastMonth, ThisYear
```

Plus 2 starter bundles for documentation/demo:

- `LipiDateRangePresets.CommonReports` — `[Today, Last7Days, Last30Days, ThisMonth, LastMonth]`
- `LipiDateRangePresets.CommonScheduling` — `[Today, Tomorrow, Next7Days, NextWeek, NextMonth]`

Real bundles emerge from module needs in Phase 4.x. The starter bundles are examples, not the production catalog.

```razor
<LipiDateRangePicker Name="report"
                     Label="Report period"
                     @bind-StartValue="_start"
                     @bind-EndValue="_end"
                     Presets="LipiDateRangePresets.CommonReports" />
```

Presets are resolved lazily — `Today` always reflects the current calendar day, not the moment the picker was constructed.

### 6.6 Open-ended ranges (E4 lock)

`AllowOpenEnd=false` (default): both ends required. Start picked → end MUST be picked to commit.

`AllowOpenEnd=true`: end can be null. After picking start, "Set as ongoing" button appears in popover footer. Click it → commits with start=picked, end=null. Field displays `13/01/2026 → ongoing`.

## 8 — Architectural decisions (the engineering calls)

### 8.1 F3 — DateSegment absorbed into InputMode=Segments

Original design considered a separate `DateSegment` for `LipiCompoundField`, mirroring `SelectSegment` and `TextSegment`. Rejected: would duplicate calendar-popover wiring (every segment needs popover access for icon click). A single `LipiDatePicker` with two render modes (`Field` | `Segments`) is simpler — one component, one popover, one parameter to switch behavior.

The trade-off: `LipiCompoundField` cannot host date-related compound shapes. If a real form needs (e.g.) a date segment alongside text segments, caller composes them inline rather than using `LipiCompoundField`.

### 8.2 A1 — ISO storage, configurable display

Database storage is always ISO 8601. Display is per-clinic. The split is locked because:

- ISO storage interoperates with all consumers (BI tools, exports, integrations).
- Display variation is purely UI; changing it doesn't migrate data.
- Both can evolve independently.

### 8.3 A2.2 — position:fixed, NOT portal (corrected from original lock)

Original Phase 2.4 design specified portal-via-JS popover (detach from DOM, append to body). Build chat objected; corrected to `position: fixed` matching LipiSelect pattern.

`position: fixed` positions relative to viewport, NOT to nearest positioned ancestor. It escapes ancestor `overflow: hidden` naturally, including modal containers. Portal pattern was over-engineering for the actual constraint.

Known limitation: ancestors with `transform`, `filter`, or `will-change` properties create new containing blocks that DO constrain `position: fixed`. None currently exist in LiPi; flag if introduced.

### 8.4 A4 — Type-aware bindings

Each component binds to the most precise type:
- `LipiDatePicker` → `DateOnly?` (no time)
- `LipiTimePicker` → `TimeOnly?` (clinic-local interpretation)
- `LipiDateTimePicker` → `DateTimeOffset?` (UTC instant + offset)
- `LipiDateRangePicker` → two separate `DateOnly?` (no time, no composite)

Rejected alternatives included a single `DateTime?` for everything (loses precision distinctions) and string-typed bindings (defeats the type system). The type-aware approach catches misuse at compile time.

### 8.5 D1 — Composition pattern over single popover for DateTime

`LipiDateTimePicker` composes `LipiDatePicker` + `LipiTimePicker` rather than implementing a unified date+time popover. Considered alternatives:

- Pattern X (chosen): compose the two pickers; no combined popover
- Pattern Y: single popover with both date grid + time fields inside
- Pattern Z: separate popovers but single parent component coordinating

Pattern Y was tempting but the popover gets crowded. Pattern Z duplicates state management. Pattern X is clean: each picker owns its UI; the parent owns the binding logic.

### 8.6 E1 — Dual binding for date range (NOT single composite)

`LipiDateRangePicker` exposes `StartValue` + `EndValue` as SEPARATE bindings, not a single `DateRange` composite. Rationale:

- Database storage always uses two columns (`start_date` + `end_date`)
- Two-way binding via `@bind-StartValue` / `@bind-EndValue` works without ceremony
- A composite would force every caller's model to define a synthetic record/class

Trade-off: two separate ValueChanged callbacks instead of one. Worth the API ergonomics.

### 8.7 Path 3 — Calendar grid duplication

`LipiDateRangePicker` duplicates the calendar grid markup from `LipiDatePicker` (within the component, in a `RenderFragment`). Per the Phase 2.3 Path 3 lock, declarative duplication is the locked default at 2-caller scale. Trigger to extract: 3rd consumer. We're at 2 now (LipiDatePicker + LipiDateRangePicker).

The 3rd consumer would be e.g. a future LipiYearMonthPicker or LipiCalendarView. Until then, the grid renders inline in each consumer.

### 8.8 Single-file `@code {}` pattern (Flag 2 lock)

All four components are single .razor files with inline `@code {}` blocks. Matches existing LiPi family pattern (LipiTextBox, LipiSelect, LipiCompoundField, LipiMultiSelect, LipiMultiCombobox). Rejected: separate `.razor.cs` code-behind files (would diverge from family).

`LipiDatePicker` is 949 lines — slightly over the ~800-line trigger for splitting via abstract base. Engineering judgment: kept single-file because abstract-base-with-single-concrete-subclass is bad architecture. Will revisit if a 2nd date picker variant ever needs to share the calendar grid logic at the C# level.

### 8.9 Step asymmetry — user input rejects, Now snaps (Flag 6 C2 lock)

`LipiTimePicker.Step` validates user input strictly (rejection) but the Now button snaps. This asymmetry IS the locked decision, NOT an inconsistency. Different intent → different behavior:

- User input represents explicit intent. Silently mutating it would surprise the user. Reject + show error preserves intent.
- Now is "fill in current moment, snapped to valid". The user clicked a button labeled "Now"; they understand the snap is part of the action.

### 8.10 LipiContainerBase NOT used for LipiDateRangePicker

`LipiContainerBase` (Phase 2.3) was designed for "container with multiple bound segments inside" via `ICompoundSegment` registration. `LipiDateRangePicker` has dual values but NOT segments — its UI is a single popover state machine, not a registry of independent child controls. Forcing it through `LipiContainerBase` would add abstract scaffolding that doesn't fit. Direct `ComponentBase` derivation with hand-rolled visual scaffolding is cleaner.

## 9 — Forward references

### 9.1 `LipiDobPicker` (deferred to Phase 4.2)

DOB-specific UX patterns:
- Confidence tag (Verified / Self-reported / Estimated / Unknown)
- Override flow (Verified DOB locked unless SysAdmin/SiteAdmin override)
- Audit trail for overrides

`LabelConfidence` parameter on `LipiDatePicker` already provides the visual pill. The dedicated `LipiDobPicker` will compose `LipiDatePicker` + override-flow UX in Phase 4.2 alongside the patient registration migration.

### 9.2 DST handling (deferred to v1.1)

`LipiDateTimePicker` composes `DateOnly + TimeOnly → DateTimeOffset` using clinic timezone offset. For India (no DST), this is unambiguous always. For DST-observing timezones:

- **Fall-back hour**: a wall-clock time like "01:30 on the day DST ends" exists TWICE (once at standard offset, once at daylight offset). Current impl picks the standard offset by .NET convention — no UI to disambiguate.
- **Spring-forward hour**: a wall-clock time like "02:30 on the day DST starts" doesn't exist at all. Current impl will likely produce an unexpected value.

Resolve when international expansion requires DST handling. Add explicit ambiguity disambiguation UI (radio: "Was this {std abbrev} or {dst abbrev}?").

### 9.3 IME composition (deferred)

CJK/IME composition fires intermediate events during composition. Auto-advance on `oninput` may fire prematurely. India + Latin scripts unaffected. Resolve when international expansion adds fields with composed-script input.

### 9.4 Smart paste (deferred)

Pasting an ISO date string (`2026-05-07`) into Field-mode date picker should parse correctly via `ParseDate` ISO fallback. Pasting into Segments mode → splits across segments with correct token mapping. Currently truncates first segment to MaxLength. Implement when real users start pasting in Segments mode.

## 10 — Known limitations

- **No relative date input** ("today + 3 days" typed). Caller computes via `DateOnly.FromDateTime(DateTime.Today.AddDays(3))`.
- **No fiscal-year presets**. India fiscal year (April-March) not in `LipiDateRangePresets`. Add to caller bundles when needed.
- **Calendar shows fixed 6 rows always**. Some months only need 4-5 rows (February non-leap, etc.). Visual padding always 6 rows for layout consistency. JUDGMENT call.
- **No keyboard nav between segments via Arrow keys**. Tab/Shift+Tab works; ArrowLeft/Right inside a segment is the native input behavior. Cross-segment arrow keys would break that.
- **Year dropdown range can be huge**. If MinDate/MaxDate not set, defaults to ±50 years from today (101 options). Year typing into the dropdown works but no type-ahead refinement.
- **No relative range presets like "Last quarter"**. The `LipiDateRangePresets` library has month-level granularity. Quarter presets emerge from caller modules.
- **DateTimeOffset display loses timezone abbreviation**. `LipiDateTimePicker.FormatValueAsString` shows date + time only. Timezone is implicit (clinic). For UI showing the explicit zone, caller appends from `IClinicTimezoneService`.

## 12 — Implementation notes

### 12.1 Memory rule #25 bullet 7 compliance

All 4 components emit standard family classes. `lipi-multi.css`-style scoped CSS files contain only Phase 2.4-specific deltas (popover, calendar grid, segments, range visualization). Field-bar heights, borders, focus rings, asterisk styling all inherit from `lipi-inputs.css`.

`LipiDateRangePicker` is the visual outlier — it doesn't inherit `LipiInputBase` so it manually emits family classes via its own `CssClasses` getter. The visual result is identical.

### 12.2 Memory rule #25 bullet 6 compliance (inheritance shadowing)

Verified during build: no `new` keyword usage. No parameters redeclared from `LipiInputBase`.

`LipiDateTimePicker` had a name collision in initial draft: `[Inject] IDateFormatService DateFormat` collided with `[Parameter] public string? DateFormat`. Resolved by renaming the injected service to `DateFmt` for this component only. The parameter keeps the user-facing name `DateFormat`. Documented inline.

### 12.3 Path 3 status post-Phase-2.4

| Pattern | Consumers |
|---------|-----------|
| LipiSelect dropdown panel | LipiSelect, SelectSegment (=2) |
| LipiMultiSelect dropdown panel | LipiMultiSelect, LipiMultiCombobox (=2) |

All three patterns are at exactly 2 consumers. All three are at the threshold for extraction. The 3rd consumer of any one of them triggers the extraction.

### 12.4 Single-file size

`LipiDatePicker.razor` at 949 lines is over the ~800-line trigger. Engineering judgment kept it inline because abstract-base-with-one-concrete-subclass is anti-pattern. If the file grows beyond ~1200 lines (e.g., on a future feature ship), revisit.

### 12.5 Forward compatibility with clinic-config schema

When `master.clinics` gains the format/timezone columns, only the service implementations change. Component code is fully isolated from the storage layer. Migration:

1. Add columns + defaults to `master.clinics` schema
2. Update `DateFormatService` + `ClinicTimezoneService` to read from `IClinicContext.CurrentClinic`
3. Components automatically pick up the new behavior — no consumer changes
