## Components covered

| Component | Generic | Use case | Sub-step |
|-----------|---------|----------|----------|
| `LipiCompoundField` | no | Multi-segment input host (Mobile, Aadhaar, Landline, future Date pickers) | 2.3 / Batch 9a |
| `SelectSegment<TValue>` | yes | Dropdown segment inside a compound field (ISD code, STD code) | 2.3 / Batch 9a |
| `TextSegment` | no | Free-text segment inside a compound field (number, group of digits) | 2.3 / Batch 9a |
| `ICompoundSegment` | — | Contract that segments implement to register with the parent container | 2.3 / Batch 9a |

`LipiCompoundField` differs structurally from the `01.2` text input family — it does NOT inherit from `LipiInputBase<TValue>` because it has no single bound value. Instead, it inherits from a NEW sibling abstract base `LipiContainerBase` that owns segment registration, focus-out aggregation, and visual scaffolding. The child segments DO inherit from the input family bases (`SelectSegment` from `LipiSelectBase`, `TextSegment` from `LipiInputBase`) — each segment binds its own `Value` and validates independently, while the parent aggregates state for the visual envelope.

## 1 — Architecture

### 1.1 Class hierarchy

```
                 ComponentBase
                       │
       ┌───────────────┼───────────────────────────────┐
       │                                               │
  InputBase<TValue>                              LipiContainerBase    ← NEW (Batch 9a)
       │                                               │
  LipiInputBase<TValue>                          LipiCompoundField
       │
       ├── LipiTextBox / LipiTextArea / LipiNumberInput<TValue>
       ├── LipiSelectBase<TValue, TItem>
       │      ├── LipiSelect<TValue>
       │      ├── LipiCombobox<TValue, TItem>
       │      └── SelectSegment<TValue>           ← NEW (Batch 9a)
       └── (direct subclass)
              └── TextSegment                      ← NEW (Batch 9a)
```

`LipiContainerBase` is a deliberate sibling to `LipiInputBase` — not a subclass, not a refactor. The two responsibilities (single bound value vs. hosting child segments) are orthogonal. See §9.2 for the architectural decision rationale.

Segments are normal `LipiInputBase`-derived components (or `LipiSelectBase`-derived) that additionally implement `ICompoundSegment`. The interface is the registration contract: every segment exposes `IsEmpty`, `IsValid`, `HasError`, `ErrorMessage`, and `FocusAsync()` to the parent so it can aggregate state and drive auto-advance.

### 1.2 Why a sibling base instead of `LipiInputBase` derivation

`LipiCompoundField` has no `Value` property to bind. Each child segment binds its own value to a separate model property. If we forced `LipiCompoundField` through `LipiInputBase<TValue>`, we'd have to invent a synthetic composite TValue (e.g., `record MobileValue(string ISD, string Number)`), bind it to a model field, and split it back into segments at render time. This would couple the compound to a specific shape and bloat every consumer's model.

The sibling-base shape preserves the natural mapping: caller binds `_model.MobileISD` to the ISD segment and `_model.MobileNumber` to the number segment. The compound exists only as a visual + behavior wrapper.

### 1.3 The `ICompoundSegment` contract

```csharp
public interface ICompoundSegment
{
    bool IsEmpty { get; }
    bool IsValid { get; }
    bool HasError { get; }
    string? ErrorMessage { get; }
    Task FocusAsync();
}
```

Segments expose their state to the parent through this interface. The parent's `ResolvedState` aggregation logic walks all registered segments via `_segments` (a `List<ICompoundSegment>` populated by `RegisterSegment` / `UnregisterSegment` in segment lifecycle hooks).

The interface is intentionally minimal. Anything more (e.g., raw value access) would couple parent to specific segment shapes and break the abstraction.

## 2 — Common parameters (`LipiCompoundField`)

`LipiCompoundField` inherits parameters from `LipiContainerBase`. The visual surface is a label + field-bar + helper layout that mirrors the `01.2` input family — same `28/32/40 px` field heights, same focus ring, same state cascade, same required-asterisk and apricot-tint behaviors.

| Parameter | Type | Default | Required | Notes |
|-----------|------|---------|----------|-------|
| `Name` | `string` | — | ✅ | Drives wrapper `id` and accessibility wiring. |
| `Label` | `string` | — | ✅ | Visible label text. |
| `Helper` | `string?` | `null` | | Below-field hint text in default state. |
| `Error` / `Warning` / `Success` | `string?` | `null` | | State-specific helper text. Aggregates with per-segment errors — see §4. |
| `Required` | `bool` | `false` | | Renders asterisk + ARIA + apricot tint when ALL segments empty. |
| `Disabled` | `bool` | `false` | | Cascades to all child segments via `[CascadingParameter]`. |
| `ReadOnly` | `bool` | `false` | | Cascades to all child segments via `[CascadingParameter]`. |
| `Size` | `InputSize` | `Medium` | | `Small` (28px) / `Medium` (32px) / `Large` (40px) field-bar height. |
| `LabelConfidence` | `ConfidenceLevel?` | `null` | | Pill next to label (Verified / Self-reported / Estimated / Unknown). |
| `RequiredVisualStyle` | `RequiredVisualStyle?` | DI default | | `ApricotTint` (default) / `AsteriskOnly`. |
| `Cols` | `int?` | `null` | | Grid-column span hint for compound rows. |
| `Class` | `string?` | `null` | | Extra wrapper class for caller-side styling. |
| `AriaDescribedBy` | `string?` | `null` | | Extra IDs to append to `aria-describedby`. |

`LipiCompoundField` does NOT have `Value` / `ValueChanged` / `ValueExpression` — those are properties of `LipiInputBase<TValue>`, which `LipiContainerBase` does not derive from. Each child segment binds its own value to a separate model property.

### 2.1 Component-specific parameters

#### `SelectSegment<TValue>`

Inherits all `LipiSelectBase<TValue, TValue>` parameters — `Items`, `ValueSelector` (defaulted to identity), `LabelSelector` (defaulted to `ToString()`), `Searchable`, `AllowFreeText`, etc. Adds:

| Parameter | Type | Default | Required | Notes |
|-----------|------|---------|----------|-------|
| `Width` | `string?` | `null` | | CSS width applied to the segment cell — e.g., `"80px"` for ISD code, `"100px"` for STD code. Default lets the segment size to its dropdown content. |
| `SegmentAriaLabel` | `string?` | `null` | | Accessible name for the segment. When parent has visible label "Mobile", segments use `SegmentAriaLabel="ISD code"` and `"Number"` so screen readers announce "Mobile, ISD code, combobox" + "Mobile, Number, edit". |

Segments still require `Name` and `Label` parameters (inherited from `LipiInputBase` with `[EditorRequired]`). The Name drives the segment's `id` for accessibility; the Label is used internally for `aria-label` fallback when `SegmentAriaLabel` is null. The visible LABEL text comes from the parent `LipiCompoundField.Label` — segment Labels are not rendered visibly.

#### `TextSegment`

Inherits all `LipiInputBase<string?>` parameters — `Type` (`text` / `tel` / `email`), `MaxLength`, `InputMode` (`numeric` / `tel` / `decimal`), `Pattern`, etc. Adds:

| Parameter | Type | Default | Required | Notes |
|-----------|------|---------|----------|-------|
| `Width` | `string?` | `null` | | CSS width applied to the segment cell. Set to fixed widths when the segment expects a known length (e.g., `"40px"` for Aadhaar 4-char groups). |
| `SegmentAriaLabel` | `string?` | `null` | | Same role as `SelectSegment.SegmentAriaLabel`. |

When `MaxLength` is set, `TextSegment` triggers auto-advance — see §5.

## 3 — The 7 states (inherited from input family)

`LipiCompoundField` uses the same 7-state cascade as the `01.2` family:

```
Disabled > ReadOnly > Error > Success > Warning > RequiredEmpty > Default
```

The wrinkle: `Error` is computed from segment aggregation, not just the parent's own `Error` parameter. See §4.1.

The state cascade resolution lives in `LipiContainerBase.ResolvedState`. The visual treatment (border color, background tint, focus ring) is identical to the `01.2` input family — both bases emit the same `.lipi-input-state-{state}` class on the wrapper, and `lipi-inputs.css` provides the styling.

## 4 — Validation flow (Q3 = C + C1)

The locked validation decision (Q3 from the strategic design package, sub-decision C1) is:

> Combined helper text from all errored segments, joined; field-level error border around the whole compound; per-segment border on each errored segment. The first failing segment's message is the primary helper text; subsequent failures append after `· ` separator.

### 4.1 Aggregation logic

`LipiContainerBase.AnyErrored` walks `_segments` and returns `true` if any segment's `HasError` is `true`. The parent's `ResolvedState` then transitions to `Error` regardless of the parent's own `Error` parameter.

```csharp
protected bool AnyErrored =>
    _segments.Any(s => s.HasError);

protected string? AggregatedHelperText
{
    get
    {
        var segmentErrors = _segments
            .Where(s => s.HasError && !string.IsNullOrEmpty(s.ErrorMessage))
            .Select(s => s.ErrorMessage)
            .ToList();
        if (segmentErrors.Count > 0) return string.Join(" · ", segmentErrors);
        if (!string.IsNullOrEmpty(Error)) return Error;
        if (!string.IsNullOrEmpty(Warning)) return Warning;
        if (!string.IsNullOrEmpty(Success)) return Success;
        return Helper;
    }
}
```

The parent's helper-text cascade prefers segment-level errors over parent-level error (the segments speak with more specificity), then falls back to parent error / warning / success / default helper.

### 4.2 Visual treatment of segment errors

Each segment has its own internal state (computed by its own `LipiInputBase` / `LipiSelectBase` machinery). When a segment's `ResolvedState == Error`, its outer markup gains the `lipi-compound-segment-error` class — applied per-segment so visually the user sees:

- Compound wrapper: red border around the entire field bar (state cascade triggered by `AnyErrored`)
- Errored segment(s): additional red border on the segment cell
- Other segments: normal styling

This makes both the field-level "something is wrong" signal and the segment-level "this specific segment is wrong" signal visible simultaneously.

### 4.3 Required + empty cascade (apricot tint)

Required-empty visual treatment uses `IsEmpty` on `LipiContainerBase`:

```csharp
protected override bool IsEmpty =>
    _segments.All(s => s.IsEmpty);
```

When `Required=true` AND ALL segments are empty AND no segment is errored, the apricot tint applies (matches the `01.2` family Q5 strict-IsEmpty behavior). Once any segment has a value, the tint clears.

## 5 — Auto-advance (Q4 = C with cursor at position 0)

The locked auto-advance decision (Q4 from the strategic design package) is:

> Smart auto-advance: when a `TextSegment` reaches its `MaxLength` AND the next segment exists, focus jumps to the next segment with the cursor at position 0. When a `SelectSegment` commits a value via dropdown selection, focus jumps to the next segment unconditionally. The last segment never auto-advances out — focus stays even after MaxLength.

### 5.1 Implementation flow

1. `TextSegment` `OnInput` handler tracks the input value.
2. When `value.Length == MaxLength`, the segment calls `Container.AdvanceFocusFromAsync(this)`.
3. `LipiContainerBase.AdvanceFocusFromAsync(ICompoundSegment from)` finds the index of `from` in `_segments`, then calls `_segments[index + 1].FocusAsync()` if a next segment exists.
4. The next segment's `FocusAsync()` sets cursor to position 0 (via JS interop for text inputs, or via opening the dropdown for selects).

### 5.2 IME and Composition (deferred)

CJK / IME composition is NOT handled in Phase 2.3. The auto-advance fires on every `OnInput` change, which during IME composition fires once per intermediate character. For Phase 2.3's scope (Mobile, Landline, Aadhaar — all numeric / Latin-only), this is acceptable. For Phase 2.4+ when international names or addresses use compound fields, the auto-advance will need to listen for `compositionend` events and only advance after composition completes.

### 5.3 Smart paste (deferred)

When user pastes a 12-digit Aadhaar into segment 1, the natural behavior would be: split across segments 1/2/3 (4-4-4) and focus the last segment. Phase 2.3 does NOT implement this — pasting a 12-digit string into segment 1 just truncates to 4 chars (the segment's MaxLength) and auto-advances normally. Smart paste is queued for Phase 2.4+ when Date pickers and other multi-segment inputs increase the value of paste handling.

## 6 — Touched-state model (Q2 = Z, focus-leaves-compound)

The locked touched-state decision (Q2 from the strategic design package, option Z) is:

> Validation messages surface only when focus leaves the entire compound, not when focus moves between segments inside it.

### 6.1 Why focus-leaves-compound, not per-segment-blur

Per-segment blur fires whenever the user tabs from segment 1 to segment 2 — but the user is still entering the compound's value, just in pieces. Showing "ISD code is required" the moment they tab to the number field would interrupt mid-flow. Better UX: aggregate touched-state at the compound level.

### 6.2 Implementation

`LipiContainerBase` exposes a `[JSInvokable] OnFocusLeftCompound()` callback. JS attaches a `focusout` listener on the wrapper element via `lipiCompound.attachFocusOut(wrapperRef, dotNetRef)`. The JS handler checks `event.relatedTarget` — if it's a descendant of the wrapper, focus stayed inside (segment-to-segment); if it's outside or null, focus actually left.

When focus leaves, `OnFocusLeftCompound` runs:

```csharp
[JSInvokable]
public void OnFocusLeftCompound()
{
    if (_isTouched) return;
    _isTouched = true;
    foreach (var seg in _segments)
        if (seg is LipiInputBaseTouchable t) t.MarkTouchedFromContainer();
    InvokeAsync(StateHasChanged);
}
```

Marking `_isTouched` on the parent AND propagating `MarkTouchedFromContainer()` to every segment ensures all segments validate, even ones the user never visited. This is critical for required-segment detection — if the user fills in segment 1 and tabs straight out without visiting segments 2 and 3, those segments still validate and show errors.

### 6.3 Why the JS-side approach (not pure C#)

Blazor's `FocusEventArgs` does NOT expose `RelatedTarget`. That's a DOM web-API property, not surfaced in the .NET event args. Pure-C# attempts to detect "did focus go inside or outside the wrapper?" require interop anyway. The JS-listener-with-DotNetObjectReference-callback pattern is the production-Blazor idiom (used by MudBlazor, Radzen, Telerik for the same scenario) and is the locked Phase 2.3 pattern for ANY focus-out / outside-click / scroll-detection logic going forward.

This pattern also covers `LipiSelectBase`'s outside-click detection (Phase 2.2) — both share the same JS interop family.

## 8 — Architectural decisions (the engineering calls)

### 8.1 Track 4b / Approach C — Generic compound over per-shape components

Rejected: per-shape components (`LipiMobileField`, `LipiAadhaarField`, `LipiLandlineField`).
Chosen: one generic `LipiCompoundField` that hosts segments.

Rationale:

- **Open shape space.** Every form's compound is unique. Per-shape components would multiply forever.
- **Composition matches the data shape.** Caller binds each segment to a separate model property — natural mapping, no synthetic composite TValues.
- **Extensibility.** Future segment types (`DateSegment`, `TimeSegment`, future custom segments) plug into the same parent without modifying it.

### 8.2 Path 3 — Declarative duplication of dropdown panel

`SelectSegment` needed the same dropdown panel markup as `LipiSelect`. Three paths considered:

- **Path 1**: extract dropdown rendering into a virtual method on `LipiSelectBase` returning `RenderFragment`.
- **Path 2**: move dropdown into a separate component imported by both.
- **Path 3**: duplicate the dropdown panel markup verbatim in `SelectSegment`.

Chosen: Path 3.

Rationale at 2-caller scale:

- **Debugging clarity.** Extraction adds an indirection layer. Method-form `RenderFragment` produces renders that don't appear in the `.razor` markup the developer is editing — debuggers step into compiled delegate code, not source markup.
- **Independent iteration.** Templates evolving per consumer is more important than DRY at 2-caller scale. `SelectSegment`'s dropdown might gain a "back to compound" button; `LipiSelect`'s might not.
- **Boundary protection.** Extraction tempts the base class to absorb consumer-specific concerns ("LipiSelect needs heading, SelectSegment doesn't, conditional flag goes on the base"). Path 3 forces each consumer to take ownership of its own markup.

**Trigger to extract**: the third consumer of any panel shape. Until then, declarative duplication is the locked default.

This decision generalizes beyond Phase 2.3 — it's the locked pattern for ANY family of components that share rendering chunks. Phase 4 modules building on Phase 2 will follow the same trigger.

### 8.3 `LipiContainerBase` as sibling base, not subclass or refactor

Rejected:

- **Option A — refactor `LipiInputBase` to support container shapes via composition.** Forces every input to carry container ceremony (segment registration, focus-out aggregation) that single-value inputs never use. Pollution.
- **Option B — make `LipiContainerBase` inherit from `LipiInputBase`.** Forces a synthetic composite TValue on the compound, which couples to specific shapes (see §1.2).

Chosen:

- **Option C — sibling abstract base.** Two responsibilities (single bound value vs. hosting child segments) are orthogonal and deserve separate inheritance trees.

Rationale:

- **Clean responsibility split.** `LipiInputBase` knows about TValue binding, EditContext subscription, parse/format. `LipiContainerBase` knows about segment registration, focus-out aggregation, container-level state cascade.
- **Reusable infrastructure.** Future container-shape components (e.g., a `LipiFormFieldGroup` that wraps multiple unrelated fields under a common label and validation envelope) inherit `LipiContainerBase` directly.

### 8.4 CSS family-rule scaffolding (memory rule #25 bullet 7)

`LipiCompoundField`'s wrapper emits the same family classes as `01.2` inputs (`lipi-input-wrapper`, `lipi-input-{size}`, `lipi-input-state-{state}`, `lipi-input-field` on the field bar). This means it inherits all family-level visual rules from `lipi-inputs.css` — same heights, borders, focus rings, asterisk style.

The Batch 9a initial ship missed this — Batch 9a deployed `LipiCompoundField` rendering at 18.4px field height because `lipi-multi.css` (then a placeholder) and `lipi-compound.css` did not duplicate the family-level height rules, AND the `lipi-inputs.css` rules at the time were keyed on compound-class selectors (`.lipi-input-medium.lipi-input-select`) that didn't match. Batch 9a.1 promoted the height rules to truly family-level shared rules keyed only on `.lipi-input-{size} .lipi-input-field`, which is the locked pattern going forward.

The architectural lesson: family-level rules belong in shared CSS keyed on family classes; per-component scoped CSS holds only genuine deltas. This is now memory rule #25 bullet 7.

## 9 — Forward references

### 9.1 `DateSegment` (Phase 2.4)

The Date/Time family will introduce `DateSegment` — a segment for day/month/year subfields under a `LipiCompoundField`. Adding it requires no `LipiContainerBase` changes; segment registration via `ICompoundSegment` is the extensibility point.

Anticipated shape:

```razor
<LipiCompoundField Name="dob" Label="Date of birth" Required="true">
    <TextSegment Name="dob-day"   Label="Day"   MaxLength="2" InputMode="numeric" />
    <TextSegment Name="dob-month" Label="Month" MaxLength="2" InputMode="numeric" />
    <TextSegment Name="dob-year"  Label="Year"  MaxLength="4" InputMode="numeric" />
</LipiCompoundField>
```

Or with a dedicated `DateSegment` that handles month-name display, calendar popups, etc.:

```razor
<LipiCompoundField Name="dob" Label="Date of birth" Required="true">
    <DateSegment Name="dob-segment"
                 @bind-Value="_model.DateOfBirth"
                 Format="DD/MM/YYYY"
                 MinDate="1900-01-01"
                 MaxDate="@DateTime.Today" />
</LipiCompoundField>
```

The exact segment surface is locked in Phase 2.4.

### 9.2 Smart paste (deferred)

Pasting a 12-digit string into Aadhaar segment 1 should auto-fill segments 2 and 3. Phase 2.3 does NOT implement this. Defer until Phase 2.4 when Date pickers and other multi-segment inputs increase the value of paste handling. Implementation will likely live in `TextSegment.OnPaste` and call a new `LipiContainerBase.DistributePastedValueAsync(string, ICompoundSegment from)` method that splits across segments respecting their MaxLength.

### 9.3 IME / composition (deferred)

CJK input methods fire `compositionstart` / `compositionupdate` / `compositionend` events. Auto-advance currently triggers on every `OnInput`, which during composition fires per intermediate character. For Phase 2.3's scope (numeric / Latin compounds), this is acceptable. Phase 4 modules with international name fields will need composition-aware auto-advance.

### 9.4 Custom segment types

Third-party callers can implement `ICompoundSegment` directly — the contract is open. Phase 2.3 ships only `SelectSegment` and `TextSegment`; future custom segments (e.g., `MaskedSegment` for credit card 4-4-4-4 with luhn check, `IpAddressSegment`, `CronSegment`) plug in identically.

## 10 — Known limitations

- **No keyboard back-navigation between segments.** Backspace at position 0 of a non-first segment does NOT focus the previous segment. Standard listbox/text-input interaction patterns don't expect this; if users request it, add via `TextSegment.OnKeyDown` listening for `Backspace` when `Value.Length == 0 && cursor == 0`.
- **No segment reordering.** Segments render in the order of their `<TextSegment>` / `<SelectSegment>` appearance in the parent's child content. There is no parameter to reorder them at render time.
- **No segment hide/show.** Each segment is always rendered. A "skip the STD code if ISD is non-Indian" pattern requires conditional `@if` in the parent's markup, not a built-in capability.
- **No nested compounds.** Putting a `LipiCompoundField` inside another `LipiCompoundField` is not supported. The `RegisterSegment` mechanism walks one level only. If needed in the future, the contract can extend, but no use case has emerged.
- **No segment-level disabled/readonly override.** When parent has `Disabled="true"`, all segments cascade to disabled. There is no way to keep one segment editable while disabling others. Same for `ReadOnly`.

## 12 — Implementation notes

### 12.1 Memory rule #25 bullet 7 compliance

`LipiCompoundField.razor`'s wrapper emits `class="@CssClasses ..."` where `CssClasses` (from `LipiContainerBase`) returns `lipi-input-wrapper lipi-compound-field lipi-input-{size} lipi-input-state-{state}`. The shared `lipi-inputs.css` family-level rules apply via the `lipi-input-wrapper` and `lipi-input-{size}` classes. The compound-specific stylesheet `lipi-compound.css` adds only:

- Field-bar flex layout (segments side-by-side)
- Segment cell borders (so each segment has its own outline within the compound bar)
- Per-segment error class (`.lipi-compound-segment-error`)

No duplicate height/border/focus-ring rules. No compound-class height selectors. The architectural cleanup happened in Batch 9a.1 (CSS sub-batch) — see CHANGE-LOG A19.

### 12.2 Segment registration flow

Each segment subscribes to the parent's `[CascadingValue]` `LipiContainerBase` reference in `OnInitialized`. The segment calls `Container.RegisterSegment(this)` once and `Container.UnregisterSegment(this)` in `Dispose`. The parent's `_segments` list is the source of truth for state aggregation and auto-advance ordering.

```csharp
// In SelectSegment.razor / TextSegment.razor @code:
[CascadingParameter] protected LipiContainerBase? Container { get; set; }

protected override void OnInitialized()
{
    base.OnInitialized();
    Container?.RegisterSegment(this);
}

public void Dispose() => Container?.UnregisterSegment(this);
```

When a segment's state changes (validation succeeds / fails), it calls `Container?.NotifyStateChanged()` to trigger parent re-render with the updated aggregate.
