## Components covered

| Component | Generic | Use case | Sub-step |
|-----------|---------|----------|----------|
| `LipiMultiSelectBase<TValue, TItem>` | yes | Abstract base — chip-style multi-selection state machine | 2.3 / Batch 9b |
| `LipiMultiSelect<TValue>` | yes | Identity-typed multi-select (TItem = TValue) | 2.3 / Batch 9b |
| `LipiMultiCombobox<TValue, TItem>` | yes (2 type args) | Templated multi-select with rich item / chip rendering | 2.3 / Batch 9c-a |

The two concrete components (`LipiMultiSelect`, `LipiMultiCombobox`) mirror the shape of the `LipiSelect` / `LipiCombobox` pair in the `01.2` family — identity selectors vs. caller-typed templates. Both inherit from `LipiMultiSelectBase` and share the same dropdown state machine, chip rendering helpers, keyboard navigation, caps enforcement, and free-text handling.

All three derive (transitively) from `LipiInputBase<List<TValue>>` and participate in `EditForm` validation, `DataAnnotationsValidator`, and the `ValidationMessage<For>` pipeline.

## 1 — Architecture

### 1.1 Class hierarchy

```
                 ComponentBase
                       │
                 InputBase<List<TValue>>     ← Microsoft.AspNetCore.Components.Forms
                       │
                 LipiInputBase<List<TValue>> ← Phase 2.2.5 — visual scaffolding,
                       │                       touched-state, EditContext wiring,
                       │                       env-gated parameter validation
                       │
                 LipiMultiSelectBase<TValue, TItem>   ← Batch 9b
                       │                              dropdown state machine,
                       │                              chip rendering helpers,
                       │                              caps enforcement,
                       │                              JS interop for outside-click
                       │                              + scroll-into-view
                       │
            ┌──────────┴──────────┐
            │                     │
   LipiMultiSelect           LipiMultiCombobox
   <TValue>                  <TValue, TItem>
   (TItem = TValue)          (caller-typed)
   Batch 9b                  Batch 9c-a
```

`LipiMultiSelectBase<TValue, TItem>` is an abstract intermediate that holds the shared state machine — exactly parallel to `LipiSelectBase<TValue, TItem>` from the `01.2` family. The two concrete subclasses differ only in how they extract value/label from items:

- `LipiMultiSelect<TValue> : LipiMultiSelectBase<TValue, TValue>` — identity selectors. `ItemValue(item) = item`, `ItemLabel(item) = item.ToString()`.
- `LipiMultiCombobox<TValue, TItem> : LipiMultiSelectBase<TValue, TItem>` — caller-provided `ValueSelector` + `LabelSelector` lambdas + optional `ItemTemplate` / `SelectedChipTemplate` `RenderFragment<TItem>`.

### 1.2 Why `LipiInputBase<List<TValue>>` (not a sibling base)

Unlike `LipiCompoundField` (which is a container with no bound value), multi-select DOES have a single bound value — it just happens to be a `List<TValue>`. The caller binds `_model.Allergies` (typed `List<string>`) via `@bind-Value` and the component manages the list contents.

Going through `LipiInputBase<TValue>` derivation gets us:

- **`@bind-Value` two-way binding** — `Value` / `ValueChanged` / `ValueExpression` parameters inherited.
- **`EditContext` integration** — automatic registration with parent `EditForm`'s validation pipeline. `[Required]` + `[MinLength(1)]` on the model property work out of the box.
- **Touched-state model** — same `_isTouched` machinery as text inputs; validation surfaces on field-level blur.
- **`CurrentValue` / `CurrentValueAsString`** — TValue-aware setters that round-trip through `TryParseValueFromString` (no-op for multi-select since values are set programmatically) and `FormatValueAsString`.

The trade-off: every Value mutation goes through `CurrentValue = newList` (Pattern B replacement, see §13.1) rather than direct list manipulation.

### 1.3 State precedence (inherited from input family)

Multi-select uses the same 7-state cascade as the `01.2` family:

```
Disabled > ReadOnly > Error > Success > Warning > RequiredEmpty > Default
```

The `RequiredEmpty` state for multi-select uses an override of `IsEmpty` that checks `Value.Count == 0` — see §10.

### 2.1 Component-specific parameters

#### `LipiMultiSelect<TValue>`

No additional parameters — identity selectors are hard-coded:

```csharp
protected override TValue? ItemValue(TValue item) => item;
protected override string ItemLabel(TValue item) => item?.ToString() ?? string.Empty;
```

The simplest API. Caller passes a list of strings (or any `TValue`), binds to a `List<TValue>` model property, gets multi-selection.

#### `LipiMultiCombobox<TValue, TItem>`

| Parameter | Type | Default | Required | Notes |
|-----------|------|---------|----------|-------|

## 4 — Required-field visual style

Strict `IsEmpty` (Q5 = A from the strategic design package):

```csharp
protected override bool IsEmpty =>
    CurrentValue is null || CurrentValue.Count == 0;
```

When `Required=true` AND `IsEmpty == true` AND `ResolvedState == Default`, the apricot tint applies. This matches `LipiTextBox` / `LipiSelect` and avoids visual inconsistency across the input family.

Rejected alternative (Q5 = B): "tint only before first interaction" — once `_isTouched`, never tint again. Rejected because it diverges from the `01.2` family. If we want family-wide change, do it as a Phase 3 visual review.

## 5 — Caps behavior

Two independent caps control different concerns:

### 5.1 `MaxSelections` — total selections cap

When `Value.Count >= MaxSelections.Value`:

- Dropdown options NOT yet selected gain `lipi-select-option-disabled` class (greyed out, non-interactive).
- A cap-reached banner renders at the top of the dropdown: "Maximum N reached. Remove a selection to add another."
- Already-selected items remain clickable for removal (toggle-off).
- Free-text "Add as new" is suppressed when at cap.

The cap is defended in TWO places:

1. `AddItem(value)` returns `false` if `MaxSelections.HasValue && Value.Count >= MaxSelections.Value`.
2. `SelectAndContinueAsync(item)` returns early if `AtMaxSelections && !IsSelected(v)` — defends against keyboard `Enter` / `Space` arriving when cap is in effect (UI shows disabled, but keyboard could otherwise bypass).

### 5.2 `MaxVisibleChips` — chip visibility cap (Q2 = α)

When `Value.Count > MaxVisibleChips.Value`:

- First `MaxVisibleChips` chips render normally (in `Value` list order).
- A "+M more" summary chip appears (where M = `Value.Count - MaxVisibleChips`).
- The summary chip is non-removable (no × button).
- Clicking the summary chip opens the dropdown with `_isFromSummaryClick = true`.

When `_isFromSummaryClick` is true, `GetFilteredOptions` returns `(Selected: alphabetical, Unselected: alphabetical)` — selected items group at top with the `SelectedHeading`, unselected below with `AvailableHeading`. This lets users see all current selections in one view and uncheck specific ones.

The flag resets to `false` in `CloseDropdownAsync` so a subsequent normal anchor click doesn't carry the sort behavior.

### 5.3 Caps interaction

`MaxSelections` and `MaxVisibleChips` are independent. Common combinations:

- `MaxSelections=3, MaxVisibleChips=null` — cap at 3, all 3 chips visible.
- `MaxSelections=null, MaxVisibleChips=5` — unlimited selection, summary chip beyond 5.
- `MaxSelections=10, MaxVisibleChips=5` — both active. User can select 6-10 items and see "+1 more"-"+5 more" summaries; when at 10 cap, dropdown disables remaining items.

## 6 — Templates (LipiMultiCombobox)

### 6.1 `ItemTemplate` — dropdown row rendering

Renders inside each `lipi-select-option` div. The component wraps `ItemTemplate` content with the multi-select checkbox indicator (`<LucideIcon Name="check-square" />` / `<LucideIcon Name="square" />`) — caller does NOT include the checkbox.

Example:

```razor
<ItemTemplate Context="dx">
    <div class="dx-row">
        <span class="dx-icd">@dx.IcdCode</span>
        <span class="dx-name">@dx.Name</span>
        <span class="dx-sev dx-sev-@(dx.Severity.ToLowerInvariant())">@dx.Severity</span>
    </div>
</ItemTemplate>
```

When `ItemTemplate` is null, falls back to `<span class="lipi-multi-option-label">@LabelSelector(item)</span>`.

### 6.2 `SelectedChipTemplate` — chip rendering

Renders inside each `lipi-multi-chip` span in the field bar. The component auto-appends the × button after the template content.

Example:

```razor
<SelectedChipTemplate Context="dx">
    <span class="dx-icd">@dx.IcdCode</span>
    <span class="lipi-multi-chip-label">@dx.Name</span>
</SelectedChipTemplate>
```

When `SelectedChipTemplate` is null, falls back to `<span class="lipi-multi-chip-label">@GetLabelForValue(v)</span>` — same as `LipiMultiSelect`.

**Critical: do NOT include a × button** in `SelectedChipTemplate`. `LipiMultiCombobox` always auto-appends one (when not Disabled / ReadOnly). Including your own would render two buttons.

### 6.3 Why two templates instead of one

The dropdown context and chip context have different layout constraints:

- **Dropdown row**: full-width, can show severity badges, dose info, multiple metadata columns.
- **Chip**: compact inline element, max-width capped, ellipsis on overflow.

The same TItem is rendered differently in each context. Forcing one template would require complex conditional logic (`@if (isInDropdown) ... else ...`) and couple the template to the rendering context, which is exactly what templating is designed to avoid.

## 7 — `AllowFreeText` constraint (Q4)

`AllowFreeText=true` requires `TValue=string` (or `string?`). When the user types unmatched text and accepts "Add 'X' as new", the typed string is added directly to `Value` as a new TValue. This only works when the storage shape IS string.

### 7.1 Validation

In `OnParametersSet`:

```csharp
_resolvedAllowFreeText = AllowFreeText;
if (AllowFreeText && typeof(TValue) != typeof(string))
{
    var msg = $"LipiMultiSelect: AllowFreeText=true requires TValue=string (or string?). " +
              $"Got TValue={typeof(TValue).Name}. Free-text input creates new values that " +
              $"cannot be synthesized for non-string types.";
    if (Env.IsDevelopment())
        throw new InvalidOperationException(msg);
    else
    {
        Log.LogError("[LipiMultiSelect] {Msg} Falling back to AllowFreeText=false.", msg);
        _resolvedAllowFreeText = false;
    }
}
```

`_resolvedAllowFreeText` is the value used at render time. The raw `AllowFreeText` parameter is NOT read directly during rendering.

### 7.2 Why not a `FreeTextParser` parameter

Considered: add `Func<string, TValue?>` parameter to let callers convert typed strings to non-string TValues. Rejected:

- **Clinical data binding to entity IDs (Guid, int)** should NOT support arbitrary user-typed values — they're data-quality risks. Pushing free-text use cases to `TValue=string` properties forces the architectural decision: "if you want free-text, you're storing the string itself, not an entity reference".
- **API surface complexity**: a parser parameter that's null for closed-list mode but non-null for free-text mode adds a configuration vector that's easy to misuse (parser returns `null` ambiguously means "rejected" or "couldn't parse"; rejected adds yet another callback).
- **Validation timing**: a parser would need to integrate with the dropdown's "Add as new" UI conditionally — complicated for one-off use cases.

### 7.3 Architectural guidance for clinical data

When binding multi-select to clinical data (ICD diagnoses, medication codes, lab tests, doctor IDs), use closed-list mode:

```razor
<!-- Closed list — TValue=Guid, free-text impossible -->
<LipiMultiCombobox TValue="Guid" TItem="DiagnosisDemo"
                   Items="@_allDiagnoses"
                   ValueSelector="@(d => d.Id)"
                   ...
                   @bind-Value="_model.DiagnosisIds" />
```

When binding to user-controlled vocabularies (allergies, tags, observation labels), use string TValue with free-text:

```razor
<!-- Free-text allowed — TValue=string -->
<LipiMultiSelect TValue="string"
                 Items="@_commonAllergies"
                 AllowFreeText="true"
                 @bind-Value="_model.Allergies" />
```

The `TValue` choice itself encodes the design intent. The env-gated constraint catches accidental misuse at compile-and-test time.

## 8 — Use case map

| Scenario | Component | TValue | TItem | Rationale |
|----------|-----------|--------|-------|-----------|
| Patient allergies (free-form list) | `LipiMultiSelect<string>` | `string` | `string` | Identity types; AllowFreeText for "NKDA" / custom entries. |
| Department tags on a record | `LipiMultiSelect<string>` | `string` | `string` | Closed enum-ish list. |
| Insurance coverage types (capped at 3) | `LipiMultiSelect<string>` | `string` | `string` | MaxSelections=3. |
| Active diagnoses (ICD-coded) | `LipiMultiCombobox<Guid, DiagnosisDto>` | `Guid` | `DiagnosisDto` | TValue=Guid for entity references; templated with ICD code + severity. |
| Current medications (with dose) | `LipiMultiCombobox<string, MedDto>` | `string` (drug code) | `MedDto` | Closed catalog of drugs; templated with dose. |
| Lab tests (with STAT badge) | `LipiMultiCombobox<string, LabDto>` | `string` (test code) | `LabDto` | Conditional badge per item. |
| Physician specialties | `LipiMultiCombobox<string, SpecialtyDto>` | `string` | `SpecialtyDto` | Icon + name in both dropdown and chip. |

The decision rule:

- **TValue is a primitive identity (string)** AND **labels match the values** AND **rich rendering not needed** → `LipiMultiSelect`.
- **TValue is an entity reference (Guid, int, custom code)** OR **rich rendering with metadata required** → `LipiMultiCombobox`.

## 9 — Validation flow

Multi-select participates in `EditForm` validation through inherited `LipiInputBase` machinery:

1. Caller annotates the model property: `[Required, MinLength(1)] public List<string> Allergies { get; set; } = new();`
2. `EditForm` + `DataAnnotationsValidator` evaluate validation when the model changes (each chip add / remove fires `EditContext.NotifyFieldChanged`).
3. When the user adds the first chip, EditContext fires validation → `_editContextError` clears.
4. When the user removes the last chip, validation re-fires → `_editContextError` set to "At least one allergy entry is required."
5. The error becomes visible only after the field is touched (focus leaves the wrapper).

### 9.1 Touched-state on multi-select

Touched-state fires when:

- The field-bar (or search input) loses focus (handled by `HandleAnchorBlur` when `_isOpen == false`).
- Any chip is removed via × click (calls `MarkFieldAsTouched` directly — explicit interaction is enough to stop hiding errors).

When `_isOpen == true` (dropdown open), focus may move between the search input and option clicks rapidly. Tabbing during dropdown-open does NOT mark touched — the user is mid-interaction.

## 11 — Field-bar height (Q1 = A)

Multi-select intentionally overrides the family-level fixed height. While the `01.2` family uses `height: {28,32,40}px`, multi-select uses `height: auto; min-height: {28,32,40}px` so the field bar grows naturally when chips wrap to multiple rows.

This override lives in `lipi-multi.css` as a compound-class selector:

```css
.lipi-multi-select.lipi-input-small  .lipi-input-field { height: auto; min-height: 28px; }
.lipi-multi-select.lipi-input-medium .lipi-input-field { height: auto; min-height: 32px; }
.lipi-multi-select.lipi-input-large  .lipi-input-field { height: auto; min-height: 40px; }
```

`LipiMultiSelect` and `LipiMultiCombobox` both emit the `lipi-multi-select` class via `LipiMultiSelectBase.CssClasses`.

This is the SECOND intentional family height override — `LipiTextArea`'s autogrow is the first. Both are documented in CHANGE-LOG A19 as legitimate component-specific deltas.

For form-grid alignment use cases, set `MaxVisibleChips` to a small N that fits one row:

```razor
<!-- Caps to fit a single 32px row in a form grid layout -->
<LipiMultiSelect TValue="string" Items="@_allergies"
                 MaxVisibleChips="3" @bind-Value="_model.Allergies" />
```

## 12 — Keyboard navigation (Q6 = MVP + Spacebar + Type-ahead)

### 12.1 In scope (Phase 2.3)

When focus is in the search input (Searchable mode) OR on the field bar (non-Searchable mode):

| Key | Behavior |
|-----|----------|
| `Backspace` | When search empty, remove last chip in `Value` list order. When search non-empty, native input backspace. |
| `ArrowDown` | If dropdown closed, open and highlight first option. If open, move highlight down (wrapping at end). Scrolls highlighted option into view. |
| `ArrowUp` | If dropdown open, move highlight up (wrapping at start). Scrolls highlighted option into view. |
| `Enter` | If dropdown closed, open. If open with highlighted item, toggle selection (add if absent, remove if present). Search clears, dropdown stays open for next add. |
| `Space` | Same as Enter (WAI-ARIA listbox toggle pattern). |
| `Escape` | Close dropdown if open. No-op if dropdown closed (does NOT blur the field). |
| `Tab` | Native tab to next form field. No focus trap on chips. |

When dropdown is open AND component is non-searchable (no search input, type-ahead mode):

- Single-character keys accumulate into a buffer with 1-second reset window.
- Buffer matches against `ItemLabel` prefix (case-insensitive).
- First matching item gets highlighted and scrolled into view.
- Buffer resets after 1 second of inactivity.

### 12.2 Backspace = last in `Value` list order (Q3 = a)

```csharp
protected void RemoveLastChip()
{
    if (CurrentValue is null || CurrentValue.Count == 0) return;
    var newList = new List<TValue>(CurrentValue);
    newList.RemoveAt(newList.Count - 1);
    CurrentValue = newList;
}
```

"Last" means the most recently added item (which is also the visually-rightmost in single-row layout). Pattern B replacement (see §13.1) — new list, not in-place mutation.

Rejected alternative (Q3 = b): "last visually" — the rightmost chip on the bottom-most row. Required DOM-coordinate inspection. Every production multi-select (Slack, GitHub, Linear, Notion) uses list-order semantics; matching that pattern is more important than visual proximity.

### 12.3 Click × on chip

Mouse-only chip removal (for now). Click handler:

```csharp
protected void HandleChipRemove(TValue value)
{
    if (Disabled || ReadOnly) return;
    RemoveItem(value);
    MarkFieldAsTouched();
}
```

`RemoveItem` uses Pattern B replacement.

### 12.4 Deferred to Phase 2.4+

| Key | Behavior (deferred) | Rationale |
|-----|---------------------|-----------|
| `ArrowLeft` / `ArrowRight` (when search empty) | Focus to chip × buttons for keyboard removal of specific chips | Production multi-select keyboard navigation through chips is genuinely complex; deferring to a focused enhancement batch when patient-flow modules surface the need. |
| `Home` / `End` (in dropdown) | First / last option | Nice-to-have; type-ahead covers most use cases. |
| `PageUp` / `PageDown` (in dropdown) | Viewport scroll | Same as above. |
| `Tab` from chip × button | Keyboard navigation through chip × buttons | Requires the ArrowLeft/Right work above. |

## 13 — Architectural decisions (the engineering calls)

### 13.1 Pattern B — Replacement, not in-place mutation

All Value mutations create a new `List<TValue>` instance and assign to `CurrentValue`:

```csharp
// AddItem — Pattern B replacement
protected bool AddItem(TValue value)
{
    if (value is null) return false;
    var current = CurrentValue ?? new List<TValue>();
    if (current.Contains(value, EqualityComparer<TValue>.Default)) return false;
    if (MaxSelections.HasValue && current.Count >= MaxSelections.Value) return false;

    var newList = new List<TValue>(current) { value };
    CurrentValue = newList;
    return true;
}
```

Same pattern for `RemoveItem`, `RemoveLastChip`, `ToggleItem`, `CommitFreeTextAsync`. Per chip add/remove, ONE `List<T>` allocation.

Rejected alternative (Pattern A): in-place mutation with `Value.RemoveAt(idx)` followed by `ValueChanged.InvokeAsync(Value)`. Rejected because:

- **EditContext change detection uses reference comparison.** In-place mutation produces the same reference; `EditContext.NotifyFieldChanged` may not detect the change.
- **Downstream framework compatibility.** EF Core change tracking, FluentValidation, ImmutableList<T> migration — all break with reference-equality on the SAME mutated list.
- **Records / immutable patterns.** Future migration to `record class TestModel { public ImmutableList<string> Allergies { get; init; } }` would require Pattern B anyway.

The cost (one allocation per user-paced operation) is negligible compared to correctness guarantees.

This pattern generalizes: any new collection-typed bound parameter (`List<T>`, `HashSet<T>`, `Dictionary<K,V>`) follows Pattern B by default in this codebase.

### 13.2 Path 3 — Declarative duplication of dropdown panel

`LipiMultiCombobox` (Batch 9c-a) duplicates the dropdown panel markup from `LipiMultiSelect` verbatim — ~80 lines of intentional copy. Rejected alternatives: extract the panel into a base method/component (Path 1) or move it into a separate component imported by both (Path 2).

Same rationale as the `01.3-CompoundField.md` §8.2 discussion: at 2-caller scale, extraction adds an indirection layer that obscures debugging, and templates iterating independently per consumer is more important than DRY.

**Trigger to extract**: the third consumer of any panel shape.

### 13.3 Identity selectors via abstract method override

`LipiMultiSelect<TValue>` provides `ItemValue` and `ItemLabel` via override:

```csharp
protected override TValue? ItemValue(TValue item) => item;
protected override string ItemLabel(TValue item) => item?.ToString() ?? string.Empty;
```

`LipiMultiCombobox<TValue, TItem>` uses caller-provided selectors:

```csharp
protected override TValue? ItemValue(TItem item) => ValueSelector(item);
protected override string ItemLabel(TItem item) => LabelSelector(item) ?? string.Empty;
```

The split mirrors `LipiSelect` / `LipiCombobox` exactly. The base `LipiMultiSelectBase` declares them as `abstract`, forcing each concrete subclass to be explicit about the mapping.

### 13.4 Q4 env-gated constraint pattern

Mirrors the `LipiButton` AriaLabel A14 pattern. The general rule: parameters whose validity depends on type-system constraints OR runtime configuration should:

1. Validate in `OnParametersSet` against the constraint.
2. Throw `InvalidOperationException` in Development with a diagnostic message including the type names.
3. Log error + use a fallback in Production via a `_resolved*` private field.
4. Renderer reads `_resolved*`, NOT the raw parameter.

Going forward, any future parameter with type-constraint requirements (e.g., a hypothetical `Searchable` requiring `TValue : IComparable`) follows this pattern.

### 13.5 JS interop signature fidelity (Path 3 extension)

When borrowing JS interop from a sibling base class (Path 3 reuse), the call signature must match exactly. `LipiSelectBase` calls `lipiInput.attachSelectHandlers(anchorRef, dotNetRef, dropdownId)` with three arguments. `LipiMultiSelectBase` initially shipped with two arguments and silently broke outside-click + scroll-reposition + flip-to-top behaviors. Batch 9b.2 fixed this.

The lesson: Path 3 reuse covers C#-side glue, not just Razor markup. Any component reusing a sibling base's JS interop API must match the signature byte-for-byte.

### 13.6 Scroll-into-view via `data-option-index`

Keyboard navigation past visible scroll region requires scrolling the highlighted option into view. The implementation (Batch 9b.3):

1. Each rendered option has `data-option-index="N"` matching its global index.
2. `lipiInput.scrollOptionIntoView(panelId, index)` finds the element by `[data-option-index="N"]` selector.
3. Calls `element.scrollIntoView({block: 'nearest'})` — only scrolls as much as needed.
4. C# calls the helper from `ScrollHighlightIntoViewAsync` after every keyboard-driven highlight change.

Three call sites: ArrowDown, ArrowUp, type-ahead match. The `LipiSelectBase` family has the same latent gap; CHANGE-LOG A19 documents the deferral.

## 14 — Known limitations

- **No `IEqualityComparer<TValue>` parameter.** Dedup uses `EqualityComparer<TValue>.Default`. For value types and strings this is correct; for record types with structural equality this is correct; for reference types with custom equality logic, the caller must implement `IEquatable<T>` on their TValue or use a primitive identity TValue (e.g., Guid Id).
- **No `Compact` mode.** The 28/32/40 px family heights apply via `min-height`; there's no "tighter" variant. Future Phase 3 density toggle could add one.
- **No keyboard chip navigation.** Documented in §12.4. ArrowLeft/ArrowRight when search empty does nothing in Phase 2.3.
- **No drag-to-reorder chips.** Chips render in `Value` list order. If reordering is needed, caller must provide UI to manipulate the underlying list.
- **No "select all" / "clear all" buttons.** Caller adds these as separate buttons if needed; not a built-in capability.
- **Free-text values can't be edited after addition.** When user types "Sulfa drugs" + Enter, a chip is added with that exact string. To change it, user removes the chip and re-adds.
- **Virtualization heuristic is fixed at >50 items.** Override via `UseVirtualization` parameter. Default heuristic doesn't account for item template complexity.
- **No async loading of `Items`.** `Items` is `IEnumerable<TItem>` and assumed to be in-memory. Async-loaded option sources require caller-managed loading + state.
